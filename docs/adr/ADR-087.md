## Korak 87 — ADR-087: Administratorski API, servisni računi i sigurne integracije

Sada projektiramo kako će druge naše aplikacije i automatizacijski sustavi moći upravljati Webmailom i određenim funkcijama Docker Mailservera.

Primjerice, možemo poželjeti da druga aplikacija automatski zatraži kreiranje mailboxa, provjeri postoji li određena adresa ili upravlja aliasima.

**Ključni cilj:** omogućiti automatizaciju bez dijeljenja Super Admin lozinki i bez izravnog pristupa Docker hostu.

### 2. Servisni računi

Predlažem uvođenje posebnih identiteta za aplikacije.

Primjerice:

| Servisni račun | Dopuštena funkcija |
|---|---|
| `mail-provisioner` | Kreiranje mailboxa u dodijeljenoj domeni |
| `alias-manager` | Upravljanje dopuštenim aliasima |
| `mail-monitor` | Čitanje zdravstvenog statusa servisa |
| `quota-reporter` | Čitanje kvota i zauzeća |
| `user-onboarding` | Zahtjevi za kreiranje Webmail korisnika |

Ovo su ilustrativni nazivi i dopuštenja, a ne stvarno kreirani računi.

Servisni račun ne smije automatski naslijediti prava Super Admina.

### 3. API ovlasti (*scopes*)

Predlažem granularna dopuštenja, primjerice:

| Scope | Funkcija |
|---|---|
| `domains:read` | Pregled autoriziranih domena |
| `mailboxes:read` | Pregled metapodataka mailboxa |
| `mailboxes:create` | Zahtjev za kreiranje mailboxa |
| `aliases:write` | Upravljanje aliasima |
| `quotas:write` | Promjena kvota |
| `users:invite` | Slanje pozivnica |
| `operations:read` | Pregled statusa vlastitih operacija |

Scope sam po sebi nije dovoljan. Pristup se dodatno ograničava na određene domene, resurse, operacije i uvjete.

Posebno osjetljive funkcije poput trajnog brisanja mailboxa, DKIM rotacije ili globalnih Postfix promjena **nećemo omogućiti običnim servisnim računima**.

### 4. Autentifikacija i tajne

Za komunikaciju aplikacija predlažem OAuth 2.0 Client Credentials, uz kratkotrajne tokene.

Povjerljivi klijenti mogu koristiti asimetričnu autentifikaciju ili mTLS tamo gdje je primjereno. Dugotrajne tajne čuvaju se preko Key/Secrets Managera iz ADR-069.

| Kontrola | Politika |
|---|---|
| Access token | Kratkog trajanja |
| Refresh token | Nije potreban za Client Credentials |
| Servisne tajne | Zasebni Secrets Manager |
| Rotacija | Kontrolirana i auditirana |
| Opoziv | Mogućnost hitnog blokiranja servisnog računa |
| Rate limiting | Po klijentu i vrsti operacije |
| Audit | Identitet klijenta, opseg, zahvat i rezultat |

### 5. Asinkrone operacije

Neke radnje poput masovnog kreiranja mailboxa mogu trajati dulje od običnog API zahtjeva.

### 6. Automatizacija ne smije zaobići odobravanje

To je najvažnije sigurnosno pravilo.

Ako ADR-086 zahtijeva dvije osobe za visokorizičnu masovnu operaciju, API ne smije omogućiti njezino izvršavanje samo zato što zahtjev dolazi od pouzdane aplikacije.

API može pripremiti i predati zahtjev. Odobravanje ostaje unutar Admin Operation Workflowa.
