## Korak 142 — ADR-142: Backup, Disaster Recovery i testiranje obnove Webmail Core platforme

Sada projektiramo **Webmail Backup & Disaster Recovery Manager**.

Prema ranijim odlukama ADR-019 i ADR-073–075 već imamo definirane osnovne zahtjeve:

- Šifrirani offsite backup s retencijom od 90 dana.
- PostgreSQL PITR (Point-in-Time Recovery).
- Ciljani **RPO od 15 minuta** za Webmail PostgreSQL podatke.
- Ciljani **RTO od 4 sata** za Webmail aplikaciju.
- Mjesečno testiranje obnove i zasebno odobravanje potpunih DR vježbi.

Sada moramo točno definirati kako se te odluke odnose na pojedine komponente Webmaila i postojeći Dovecot.

### 2. Što moramo zaštititi?

| Komponenta | Backup strategija |
|---|---|
| `webmail_db` | Base backup + kontinuirano arhiviranje WAL-a |
| Verzionirani nacrti | PostgreSQL + povezane MIME/datotečne kopije |
| Privremeni file store | Samo objekti koje je nužno obnoviti |
| Credential Broker | Šifrirane tajne + odvojeni recovery ključevi |
| Konfiguracija | Verzije iz Git repozitorija + sigurna runtime konfiguracija |
| Security audit | Integritet i zasebna offsite evidencija |
| Redis | Rekonstrukcija prolaznog stanja iz PostgreSQL-a |
| Dovecot | Postojeći zasebni mailserver backup |

Posebno je važno da recovery ključevi ne budu pohranjeni samo unutar istog backupa koji trebaju otključati.

### 3. Konzistentnost baze i datoteka

Ne želimo situaciju da obnovimo PostgreSQL bazu, ali nedostaju datoteke na koje zapisi upućuju.

Zato predlažem **Recovery Manifest**.

Manifest evidentira identifikator backupa, vremensku točku, verziju sheme, relevantne datotečne objekte i njihove SHA-256 vrijednosti.

Budući da se PostgreSQL i datotečna pohrana ne mogu jednostavno atomarno snapshotirati kao jedna transakcija, trebamo koristiti trajan zapis objekata i reference koje omogućuju rekonstrukciju i provjeru konzistentnosti.

### 6. Poseban problem: SMTP operacije nakon obnove

Ovo je najvažnija sigurnosna kontrola u DR postupku.

Ako vratimo bazu na ranije stanje, neki `send_operation_id` zapisi možda više neće odražavati SMTP radnje koje su se dogodile nakon te vremenske točke.

**Ne smijemo automatski nastaviti slanje poruka na temelju obnovljenog reda poslova.**

Predlažem zasebni `recovery_mode` koji:

- Blokira SMTP replay.
- Blokira automatsko izvršavanje neizvjesnih vanjskih operacija.
- Zahtijeva rekonstrukciju stanja iz dostupnih pouzdanih evidencija.
- Označava nejasne operacije kao `needs_review`.
- Dopušta nastavak samo nakon provjere i zasebnog Super Admin GO.

To je u skladu s ADR-074.

### 7. Tajne i ključevi tijekom obnove

Credential Broker mora moći obnoviti zaštićene vjerodajnice bez njihovog ispisivanja u logove.

Potrebna nam je zaštita od situacije u kojoj imamo valjani backup šifriranih podataka, ali nemamo odgovarajuću verziju ključa.

Predlažem da svaka šifrirana tajna ima `key_version`, a DR runbook opisuje siguran dohvat potrebnih recovery ključeva.

Pristup ključevima mora biti odvojen od pristupa backup spremištu.

### 8. Automatska provjera backupa

Prema ADR-075 predlažem mjesečno testiranje obnove u izoliranom okruženju.

| Provjera | Kriterij |
|---|---|
| Backup postoji | Potvrđen |
| Manifest i hash | Ispravni |
| PostgreSQL restore | Uspješan |
| Alembic kompatibilnost | Potvrđena |
| Datotečne reference | Konzistentne |
| Secrets recovery | Testiran bez izlaganja tajni |
| Audit integritet | Potvrđen |
| SMTP replay blokada | Funkcionalna |
| IMAP reconciliation | Uspješan u testnom okruženju |
| RPO/RTO | Izmjereni |

Automatska provjera ne smije uključivati stvarno slanje e-mailova ili promjene produkcijskog Dovecota.

### 9. Plan oporavka

Predlažem sljedeće razine incidenta:

| Incident | Strategija |
|---|---|
| Pad Webmail API-ja | Restart samo aplikacijskog servisa |
| Pad workera | Siguran nastavak trajnih poslova |
| Redis gubitak | Rekonstrukcija prolaznog stanja |
| Oštećen PostgreSQL | PITR + reconciliation |
| Gubitak datotečne pohrane | Restore + provjera referenci |
| Kompromitiran ključ | Incident response i kontrolirana rotacija |
| Gubitak cijelog servera | Odvojeni infrastrukturni i mailserver DR postupak |

Pritom Webmail restore ne smije automatski mijenjati konfiguraciju produkcijskog Postfixa ili Dovecota.

### 10. Granice implementacije

**Paket 1:** definiramo backup manifest, konfiguracijski model, recovery mode i testne procedure.

**Paket 4:** povezujemo operativne backup i monitoring kontrole.

**Paket 5:** obvezni restore testovi i mjerenje RPO/RTO prije produkcijskog cutovera.

Nijedan od tih koraka ne počinje bez zasebnog implementacijskog GO.
