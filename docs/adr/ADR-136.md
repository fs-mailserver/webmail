## Korak 136 — ADR-136: Sigurnost Service Workera, CSP i zaštita Next.js aplikacije

Sada projektiramo **Webmail Browser Security Layer**.

Ovaj modul posebno je važan jer Webmail obrađuje HTML poruke koje mogu sadržavati zlonamjerne poveznice, skripte i pokušaje krađe podataka.

Naš cilj je zaštititi korisničke sesije, offline podatke i komunikaciju s FastAPI backendom.

### 2. Content Security Policy

Predlažem strogu CSP politiku za Webmail aplikaciju.

| Direktiva | Predložena politika |
|---|---|
| `default-src` | `'self'` |
| `script-src` | Nonce/hash, bez `unsafe-eval` |
| `object-src` | `'none'` |
| `base-uri` | `'none'` |
| `frame-ancestors` | `'none'` |
| `form-action` | `'self'` |
| `connect-src` | Samo odobreni API/WS origin |
| `img-src` | Vlastiti resursi i kontrolirane `blob:` slike |
| `worker-src` | Vlastiti Service Worker |
| `upgrade-insecure-requests` | HTTPS okruženja |

Za Next.js moramo provjeriti kompatibilnost stvarnog renderiranja s nonce pristupom. Ne želimo dodati `unsafe-inline` samo da uklonimo CSP pogreške.

CSP je dodatna zaštita; **ne zamjenjuje pravilnu sanitizaciju HTML poruka**.

### 3. Izolacija HTML e-mailova

Prema ADR-038, HTML sadržaj mora biti sanitiziran i prikazan izolirano.

Predlažem:

- Renderiranje HTML poruka u strogo sandboxiranom iframeu, po mogućnosti na zasebnom originu bez korisničke sesije.
- Uklanjanje skripti, obrazaca, event handlera i opasnih URL shema.
- Blokirane udaljene slike prema zadanim postavkama.
- Kontrolirani pristup inline CID slikama nakon provjere.
- Otvaranje vanjskih poveznica uz odgovarajuće sigurnosne atribute i phishing upozorenja.

Ako je HTML e-mail prikazan na zasebnom originu, taj origin ne smije imati pristup glavnim aplikacijskim kolačićima, IndexedDB pohrani ili Service Workeru Webmaila.

### 4. Zaštita od XSS-a

Webmail mora tretirati sva polja poruke kao nepouzdane podatke, uključujući Subject, From, nazive privitaka i sadržaj poruke.

| Kontrola | Pravilo |
|---|---|
| React escaping | Standardno sigurno renderiranje teksta |
| HTML sanitizacija | Samo kroz provjereni centralni renderer |
| `dangerouslySetInnerHTML` | Zabranjen izvan kontroliranog renderera |
| Trusted Types | Gdje preglednik podržava |
| MIME sanitizacija | Prije previewa |
| URL validacija | Odbacivanje opasnih shema |
| Dependency scanning | CI sigurnosna provjera |

### 5. CSRF i sesije

Prema ADR-020, ADR-022 i ADR-126 koristimo server-side sesije.

Predlažem sljedeće sigurnosne kontrole:

| Područje | Politika |
|---|---|
| Cookie | `HttpOnly`, `Secure`, odgovarajući `SameSite` |
| CSRF token | Za promjene stanja |
| Origin provjera | Za osjetljive zahtjeve |
| Session rotation | Nakon prijave i važnih promjena |
| Logout | Opoziv sesije na serveru |
| WebSocket | Autorizacija pri uspostavi i promjeni prava |
| CORS | Samo izričito dopušteni origin |
| Rate limits | Prijave i osjetljive operacije |

Za WebSocket nije dovoljno provjeriti samo postojanje session cookieja. Potrebna je provjera dopuštenog Origina i valjanosti sesije.

### 6. Sigurnost Service Workera

Service Worker ima širok utjecaj na PWA, zato mora imati strogo ograničenu funkciju.

Predlažem:

| Pravilo | Politika |
|---|---|
| API caching | Bez automatskog spremanja privatnih API odgovora |
| Auth endpointi | Network-only, bez cachea |
| Service Worker scope | Ograničen na Webmail aplikaciju |
| App shell | Dopušten kontrolirani cache |
| Offline poruke | Upravljani šifrirani IndexedDB |
| Cache verzije | Verzije i sigurne migracije |
| Logout | Best-effort lokalno čišćenje |
| Revoked session | Blokada daljnjih online pristupa |
| SW update | Kontrolirani update i oporavak |

Osjetljivi odgovori trebaju koristiti odgovarajuće `Cache-Control` zaglavlje, primjerice `no-store`, gdje je primjenjivo.

Service Worker ne smije automatski preuzimati cijele mailboxe niti čuvati vjerodajnice.

### 7. Offline šifriranje

Prema ADR-135, offline poruke i nacrti šifriraju se prije upisa u IndexedDB.

Predlažem koristiti Web Crypto API i autentificirano šifriranje, primjerice AES-GCM.

Ključ se izvodi iz zasebne korisničke offline lozinke pomoću odgovarajućeg KDF-a, s parametrima koje možemo prilagođavati uređaju i sigurnosnim zahtjevima.

Ključ se ne sprema trajno u čitljivom obliku. Nakon zatvaranja ili zaključavanja offline spremnika ponovno je potrebna korisnička radnja.

Važno je da ovo štiti pohranjene podatke, ali ne pruža potpunu zaštitu od kompromitiranog preglednika ili aktivnog XSS napada dok je spremnik otključan.

### 8. Sigurnost vanjskih poveznica

HTML e-mail može sadržavati poveznice koje izgledaju kao legitimne adrese, ali vode na druge domene.

Predlažem da Webmail:

- Prikazuje stvarni URL prije otvaranja.
- Upozorava na sumnjive domene i nesklad između teksta i odredišta.
- Koristi `noopener` i `noreferrer` pri otvaranju novih kartica.
- Ne dopušta opasne URL sheme poput `javascript:`.
- Ne učitava udaljene resurse bez dopuštenja.

Ovo se povezuje s phishing zaštitom iz ADR-039.

### 9. Testovi prihvaćanja

Prije prihvaćanja Core verzije moramo proći:

| Test | Očekivani rezultat |
|---|---|
| XSS u HTML poruci | Skripta se ne izvršava |
| Zlonamjerni Subject | Sigurno se prikazuje kao tekst |
| CSRF zahtjev | Odbijen |
| WebSocket s nedopuštenog origina | Odbijen |
| Opozvana sesija | Daljnji zahtjevi blokirani |
| Service Worker cache | Nema privatnih API odgovora |
| Offline ključ | Nije trajno pohranjen u čitljivom obliku |
| CSP | Nema nepotrebnih iznimki |
| Vanjska poveznica | Sigurno otvaranje |
| PWA ažuriranje | Nema gubitka valjanih offline nacrta |
