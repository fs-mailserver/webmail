## Korak 138 — ADR-138: Administratorski model Webmaila, upravljanje domenama i privilegirane operacije

Sada projektiramo **Webmail Administration & Privileged Operations Architecture**.

Već smo potvrdili tri korisničke uloge, centralni Mail Admin Console i izolirani Mail Admin Agent. U ovom koraku moramo točno definirati granicu između:

- upravljanja samom Webmail aplikacijom,
- upravljanja stvarnim Postfix/Dovecot računima,
- pristupa privatnom sadržaju korisničke pošte.

To su tri različite razine odgovornosti.

### 2. Administratorske uloge

| Uloga | Ovlasti |
|---|---|
| **Super Admin** | Globalna konfiguracija Webmaila, upravljanje domenama i administratorima, odobrene privilegirane operacije |
| **Admin** | Korisnici, mailboxi i konfiguracija samo unutar dodijeljenih domena |
| **User** | Vlastiti račun, dopušteni mailboxi i osobne postavke |

**Administrator nije automatski ovlašten čitati tuđu poštu.** Pristup sadržaju zahtijeva zaseban, izričito dodijeljen i auditiran mailbox grant, odnosno posebno kontrolirani break-glass postupak iz ADR-066.

### 3. Koje operacije izvodi koja komponenta?

| Operacija | Izvršitelj |
|---|---|
| Kreiranje Webmail korisnika | FastAPI + PostgreSQL |
| Dodjela Webmail role | Admin Control Plane |
| Dodjela mailbox prava | Authorization Service |
| Suspenzija Webmail računa | Identity Service |
| Kreiranje stvarnog mailboxa | Izolirani Mail Admin Agent |
| Promjena Dovecot kvote | Mail Admin Agent |
| Upravljanje Postfix aliasima | Mail Admin Agent |
| Upravljanje domenama u mailserveru | Mail Admin Agent |
| Provjera DNS zapisa | Kontrolirani dijagnostički servis |
| Postfix queue akcije | Mail Admin Agent uz posebnu autorizaciju |

Sama dodjela mailbox granta ne znači da je mailbox fizički kreiran niti da postoje valjane IMAP vjerodajnice.

### 5. Predloženi model podataka

Koristimo modularne sheme iz ADR-125.

| Tablica | Namjena |
|---|---|
| `access.role_assignments` | Globalne i domenske uloge |
| `access.mailbox_grants` | Granularna mailbox prava |
| `system.domains` | Registrirane i dopuštene domene |
| `system.admin_operations` | Trajna evidencija administrativnih zahtjeva |
| `system.admin_approvals` | Neovisna odobrenja |
| `system.configuration_changes` | Verzije konfiguracijskih promjena |
| `audit.admin_events` | Administrativni audit |

Za `admin_operations` predlažem identifikatore `operation_id`, `actor_id`, `target_ref`, `action`, `status` i `correlation_id`.

Ne spremamo administrativne tajne ili čitljive lozinke u audit.

### 6. Razine rizika

Ne trebaju sve administrativne radnje jednaku razinu kontrole.

| Razina | Primjer | Kontrola |
|---|---|---|
| Niska | Pregled konfiguracije | RBAC |
| Srednja | Pozivanje novog korisnika | RBAC + audit |
| Visoka | Kreiranje mailboxa, promjena kvote ili aliasa | Step-up, Dry Run, audit |
| Kritična | Masovno brisanje, promjena globalnih ovlasti ili break-glass | Neovisni odobravatelj, dodatne provjere |

Trajno brisanje mailboxa dodatno podliježe ADR-010 i Legal Hold pravilima.

Neovisni odobravatelj mora biti različita ovlaštena osoba. Sustav ne smije zaobići to pravilo ako trenutno postoji samo jedan administrator.

### 7. Kontrola stvarnog stanja

Moramo razlikovati **željeno stanje** u Webmail bazi i **stvarno stanje** mailservera.

Primjerice, Admin Console može prikazati zahtjev za kreiranje mailboxa kao `pending`, ali ga ne smije prikazivati kao kreiran dok Agent ne potvrdi rezultat.

Predlažem statuse:

`requested → validated → approved → executing → verified`

Uz završne statuse `failed`, `rejected` ili `needs_review`.

Kod prekida komunikacije s Agentom ne ponavljamo automatski rizične operacije prije provjere stvarnog stanja.

### 8. Zaštita izoliranog Agenta

Agent mora imati:

- Strogo definiranu listu dopuštenih operacija.
- Minimalne privilegije potrebne za konkretnu operaciju.
- Autentificiranu komunikaciju s kontrolnim slojem.
- Provjeru identiteta zahtjeva i zaštitu od ponavljanja.
- Validaciju dopuštenih domena, mailboxa i parametara.
- Zaseban audit izvršavanja.

Ne smijemo pretpostaviti da sve radnje možemo izvesti bez promjene postojeće mailserver konfiguracije. To će biti predmet izolirane provjere prije implementacije.

### 9. Granice implementacije

**Paket 1 — Foundation & Security:** modeli uloga, autorizacija, API ugovori i simulirani Admin Agent.

**Paket 4 — Admin & Operations:** stvarni Admin Console i integracija s Agentom u izoliranom testnom okruženju, nakon zasebnog GO.

Promjene produkcijskih Postfix/Dovecot mailboxa, domena ili konfiguracije i dalje zahtijevaju posebna odobrenja.
