## Korak 128 — ADR-128: IMAP sinkronizacija, checkpointi i usklađivanje PostgreSQL-a s Dovecotom

Sada detaljno projektiramo **IMAP Synchronization Engine**.

Ovaj modul mora pouzdano sinkronizirati mailboxe, čak i kada korisnik ima više računa, kada se poruke mijenjaju u drugim IMAP klijentima ili kada dođe do prekida mreže.

Najvažnije pravilo ostaje:

**Dovecot je izvor istine za e-mailove. PostgreSQL služi za indeksiranje, ubrzavanje pretrage i aplikacijske metapodatke.**

### 2. Identitet poruke

Za identifikaciju pojedine IMAP poruke koristimo kombinaciju:

`mailbox_id + folder_id + UIDVALIDITY + UID`

Vanjski `Message-ID` koristimo kao metapodatak, ne kao jedinstveni ključ.

U PostgreSQL-u predlažem jedinstveno ograničenje nad stvarnim IMAP identitetom poruke, zajedno sa stabilnim internim `message_ref`.

To sprječava da dvije sinkronizacije slučajno kreiraju dva zapisa za istu IMAP poruku.

### 3. Strategija sinkronizacije

Zadržavamo odluke iz ADR-031–033, a sada ih povezujemo s konkretnim modelom izvođenja.

| Situacija | Postupak |
|---|---|
| Prvo povezivanje | Najnovije poruke prvo |
| Normalna sinkronizacija | QRESYNC ako je podržan |
| Bez QRESYNC-a | CONDSTORE + dodatna UID provjera |
| Bez CONDSTORE-a | Sigurni periodički UID/flag reconciliation |
| Nova poruka | Upis u indeks i osvježavanje stanja |
| Promjena zastavice | Sinkronizacija s Dovecotom |
| Premještanje | Usklađivanje izvorišne i odredišne mape |
| Brisanje | Uklanjanje iz aktivnog indeksa prema ADR-034 |
| Promjena UIDVALIDITY | Nova generacija sinkronizacije |
| Prekid veze | Siguran nastavak iz potvrđenog checkpointa |

Ne pretpostavljamo da će svaki IMAP server podržavati sve ekstenzije. Prije implementacije moramo provjeriti koje mogućnosti stvarno izlaže naš Dovecot.

### 4. Trajni checkpointi

Predlažem tablicu `mail.sync_checkpoints`.

| Polje | Namjena |
|---|---|
| `mailbox_id` | Mailbox |
| `folder_id` | IMAP mapa |
| `uidvalidity` | Identitet generacije mape |
| `highest_modseq` | Poznata MODSEQ vrijednost |
| `last_uid` | Posljednji obrađeni UID |
| `sync_generation` | Interna generacija sinkronizacije |
| `last_success_at` | Posljednja uspješna sinkronizacija |
| `status` | Stanje sinkronizacije |
| `fencing_token` | Zaštita od zastarjelog workera |

**Checkpoint se pomiče tek nakon uspješnog, trajnog upisa odgovarajućih promjena u PostgreSQL.**

Ako worker padne između obrade i potvrde, sljedeći pokušaj mora moći sigurno ponovno obraditi iste događaje.

### 5. Zaštita od paralelnih workera

Već smo u ADR-032 definirali PostgreSQL lease i fencing.

Sada predlažem da svaki posao sinkronizacije dobije privremeno vlasništvo nad konkretnim mailboxom ili mapom, uz jasno definiranu granicu paralelizma.

To je ključna zaštita od oštećenja indeksa uslijed paralelnih procesa.

### 6. Što ako se promijeni UIDVALIDITY?

Ovo je jedno od najvažnijih IMAP pravila.

Kada se UIDVALIDITY promijeni, ranije UID vrijednosti više se ne mogu smatrati identitetima istih poruka.

Predlažem:

- Označiti postojeću generaciju mape zastarjelom.
- Zaustaviti upis zastarjelih UID referenci u aktivni indeks.
- Pokrenuti novu sinkronizaciju za mapu.
- Postupno rekonstruirati indeks.
- Prikazati korisniku da je pretraga privremeno nepotpuna.

Originalne poruke u Dovecotu ostaju netaknute.

### 7. Reconciliation i provjera ispravnosti

Čak i kada QRESYNC radi, sustav mora povremeno provjeravati usklađenost stanja.

Predlažem periodičke provjere broja poruka, UID raspona, zastavica i checkpointa, uz mogućnost dublje provjere kada se pojavi odstupanje.

Tijekom obnove indeksa ne smijemo prikazivati stare rezultate kao da su aktualni.

### 8. Sigurnost sinkronizacije

| Kontrola | Pravilo |
|---|---|
| IMAP autentifikacija | Preko Credential Brokera |
| Pristup mailboxu | Granularna autorizacija |
| TLS | Obvezan |
| Worker lease | Sprječava paralelno potvrđivanje |
| Idempotencija | Ponovljeni događaj ne duplicira zapis |
| Secrets | Bez vjerodajnica u logovima |
| Rate limiting | Ne opterećuje Dovecot |
| Recovery | Nastavak iz trajnih checkpointa |
| Audit | Sigurnosno relevantne promjene |

Pozadinski indeksni poslovi ne smiju dobiti više prava nego što je potrebno za dopušteni mailbox. Gubitak ovlasti mora spriječiti daljnji neovlašteni pristup.
