## Original pre-approval proposal


## Korak 74 — ADR-074: Redoslijed oporavka servisa i automatska provjera nakon incidenta

Sada definiramo **Disaster Recovery Orchestrator**, odnosno postupak kojim ćemo vratiti Webmail u funkciju nakon ozbiljnog incidenta.

Naš dedicated server ima više servisa, a Webmail ovisi o PostgreSQL-u, Dovecotu, Redis servisu, tajnama i mrežnoj infrastrukturi.

**Najvažnije pravilo:** tijekom oporavka ne smijemo pokrenuti workere koji bi prije provjere stanja ponovno poslali zakazane poruke ili izmijenili IMAP podatke.

Ovaj redoslijed označava **kontrolne faze**, a ne zahtjev da, primjerice, cijeli Dovecot mora biti potpuno obnovljen prije pokretanja PostgreSQL-a. Ovisnosti ćemo precizno provjeriti za stvarnu infrastrukturu.

### 2. Recovery Mode

Predlažem poseban način rada `RECOVERY_MODE`, u kojem su osjetljive automatske operacije privremeno zaustavljene.

| Komponenta | Tijekom oporavka |
|---|---|
| Next.js / FastAPI | Read-only administrativna dijagnostika |
| IMAP sinkronizacija | Zaustavljena dok se ne provjere checkpointi |
| Send Later | Slanje blokirano |
| Celery scheduler | Izvršavanje osjetljivih zadataka blokirano |
| CalDAV / CardDAV | Dvosmjerni upisi blokirani |
| AI workers | Obrada privremeno zaustavljena |
| Postfix | Zasebno kontroliran, bez slijepog pražnjenja reda |
| Audit | Evidentira sve korake oporavka |

Važno je da Recovery Mode bude proveden na backendu i workerima. Nije dovoljno samo sakriti gumbe u Next.js sučelju.

### 3. Automatski Recovery Health Check

Nakon obnove sustav mora provjeriti ključne funkcije.

| Provjera | Kriterij prolaza |
|---|---|
| PostgreSQL | Integritet i dostupnost baze |
| Dovecot IMAP | Testna prijava i pristup mapama |
| Postfix SMTP | Kontrolirani test u sigurnom testnom opsegu |
| Secrets Manager | Ključevi dostupni autoriziranim servisima |
| Webmail autentifikacija | Prijava i MFA provjera |
| IMAP checkpointi | Nema nekontroliranog ponavljanja sinkronizacije |
| Send Later | Nema neprovjerenih ponovnih slanja |
| WebSocket | Uspostava veze i prijenos testnog događaja |
| Audit | Mogućnost pouzdanog zapisivanja događaja |

Test SMTP-a ne smije slučajno poslati stvarne poruke klijentima.

### 4. Posebno važan scenarij — Send Later

Zamislimo da je poruka zakazana za 09:00, Postfix ju je prihvatio u 09:00:02, a server se srušio prije nego što je Webmail zabilježio rezultat.

Nakon obnove, zadatak može izgledati kao neizvršen.

Zato uvodimo:

- Trajni identifikator zakazanog slanja.
- Evidenciju pokušaja SMTP predaje.
- Provjeru dostupnih Postfix dokaza o prihvaćanju.
- Status `delivery_unknown` kada nema pouzdane potvrde.
- Zabranu automatskog ponavljanja slanja s nepoznatim ishodom.

Ovo je nastavak sigurnosnog modela iz ADR-051.
