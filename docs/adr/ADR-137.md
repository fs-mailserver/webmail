## Korak 137 — ADR-137: Passkey, MFA, oporavak računa i upravljanje sesijama

Sada detaljno definiramo **Authentication Lifecycle Manager**.

Prema ADR-064 i ADR-126 već smo odlučili da Webmail koristi Passkey-first autentifikaciju, uz lozinku i MFA kao alternativni način prijave.

U ovom koraku projektiramo kako korisnik prvi put aktivira račun, dodaje uređaje, oporavlja pristup i sigurno upravlja sesijama.

### 3. Načini prijave

| Metoda | Politika |
|---|---|
| Passkey / WebAuthn | Preferirani način prijave |
| Lozinka + TOTP | Alternativni način |
| Recovery codes | Jednokratna rezervna metoda |
| E-mail recovery | Samo kao dio kontroliranog oporavka |
| IMAP lozinka | Nije način prijave u Webmail |

Passkey treba koristiti WebAuthn provjeru porijekla zahtjeva, RP ID-a, challengea i odgovarajućih autentifikatorskih svojstava.

Kod administratorskih računa zahtijevamo pouzdanu potvrdu korisničke prisutnosti i provjere korisnika u skladu s odabranom politikom autentifikacije.

### 4. MFA i Step-up Authentication

Ne želimo da jedna davno otvorena sesija bude dovoljna za osjetljive administrativne radnje.

Predlažem **step-up autentifikaciju**.

| Operacija | Dodatna potvrda |
|---|---|
| Čitanje vlastite pošte | Aktivna sesija |
| Slanje poruke | Aktivna sesija + `send` ovlast |
| Promjena lozinke | Nedavna ponovna autentifikacija |
| Dodavanje Passkeya | Nedavna ponovna autentifikacija |
| Promjena MFA metoda | Nedavna ponovna autentifikacija |
| Prikaz recovery kodova | Ponovna autentifikacija |
| Rotacija IMAP tajni | Ponovna autentifikacija |
| Administrativne promjene ovlasti | Step-up + RBAC |
| Break-glass pristup | Step-up + neovisni odobravatelj prema ADR-066 |

Za posebno osjetljive akcije predlažem da potvrda vrijedi najviše pet minuta, uz mogućnost strože politike.

### 5. Oporavak računa

Oporavak je najosjetljiviji dio autentifikacije.

Predlažem različite postupke za obične i administratorske korisnike.

| Situacija | Postupak |
|---|---|
| Izgubljen jedan uređaj | Prijava drugim Passkeyem |
| Izgubljeni svi Passkeyi | Recovery kod + dodatna provjera |
| Izgubljen TOTP | Recovery kod ili kontrolirani recovery |
| Nema nijedne metode | Administrativno pokrenut recovery uz provjeru identiteta |
| Super Admin recovery | Stroža procedura, neovisno odobrenje i audit |

Jednokratni recovery kodovi moraju biti spremljeni kao verifikatori, a korisniku prikazani samo prilikom izdavanja ili sigurne regeneracije.

**E-mail poruka sama po sebi ne smije biti dovoljna za preuzimanje administratorskog računa.**

### 6. Upravljanje sesijama

Predlažem sljedeće početne vrijednosti:

| Parametar | Prijedlog |
|---|---|
| Neaktivnost obične sesije | 12 sati |
| Maksimalno trajanje sesije | 7 dana |
| Neaktivnost Admin sesije | 30 minuta |
| Maksimalno trajanje Admin sesije | 12 sati |
| Step-up potvrda | Najviše 5 minuta |
| Recovery pozivnica | 15 minuta |
| Maksimalno neuspjelih prijava | Adaptivno ograničenje, ne samo fiksni broj |

Ovo su projektne vrijednosti koje trebamo potvrditi i testirati prije implementacije.

Administratorske sesije ne smiju ostati aktivne beskonačno zbog uključenog Remember Me načina.

### 8. Opoziv pristupa

Kada se sesija opozove:

- API zahtjevi moraju biti odbijeni.
- WebSocket konekcije prestaju imati valjanu autorizaciju.
- Push pretplate povezane s uređajem moraju se opozvati gdje je izvedivo.
- Aktivni IMAP poslovi moraju poštovati opozvana mailbox prava.
- PWA pokreće čišćenje lokalnog cachea kada ponovno dobije kontrolu.

Ostaje ograničenje iz ADR-135: uređaju koji je offline ne možemo zajamčiti trenutno brisanje već preuzetog sadržaja.
