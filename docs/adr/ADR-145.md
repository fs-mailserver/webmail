## Korak 145 — ADR-145: Release Management, verzioniranje, migracije i produkcijski GO

Sada projektiramo **Webmail Release & Change Control Manager**.

Glavni cilj je jednostavan: **niti jedan agent, GitHub workflow ili automatizacija ne smije samostalno promijeniti produkcijski Webmail ili mailserver.**

### 2. Razdvajamo pet vrsta odobrenja

Ovo je temeljno pravilo našeg projekta.

| Odobrenje | Što dopušta | Što ne dopušta |
|---|---|---|
| **Implementation GO** | Izradu određenog paketa | Merge i deployment |
| **PR Merge GO** | Spajanje provjerenog PR-a | Produkcijske promjene |
| **Staging GO** | Aktivaciju u izoliranom okruženju | Pristup produkcijskim mailboxima |
| **Pilot GO** | Točno definirani pilotski pristup | Opći cutover |
| **Production GO** | Konkretan odobreni deployment | Buduće deploymente bez novog GO |

Svaki GO odnosi se na **točno određenu radnju i opseg**. Ne prenosimo odobrenje automatski na kasnije verzije.

### 3. Verzioniranje

Predlažem Semantic Versioning za Webmail aplikaciju.

| Primjer | Značenje |
|---|---|
| `0.1.0` | Početna razvojna verzija |
| `0.5.0-rc.1` | Release kandidat |
| `1.0.0` | Prva prihvaćena Core verzija |
| `1.0.1` | Kompatibilna korekcija |
| `1.1.0` | Nova kompatibilna funkcionalnost |
| `2.0.0` | Potencijalno nekompatibilna promjena |

Ovo su ilustrativne oznake, ne postojeće objavljene verzije.

Svaki release mora biti vezan uz konkretan Git commit, digest kontejnerske slike i skup migracija.

### 4. Release Manifest

Predlažem strukturirani zapis za svaki release kandidat.

| Polje | Namjena |
|---|---|
| `release_id` | Jedinstveni identifikator |
| `version` | Verzija aplikacije |
| `git_commit` | Točan izvorni kod |
| `image_digests` | Točne kontejnerske slike |
| `api_contract_version` | OpenAPI kompatibilnost |
| `db_revision` | Alembic verzija |
| `feature_flags` | Odobreni skup funkcija |
| `acceptance_report` | Rezultati testova |
| `backup_checkpoint` | Potvrda sigurnosne kopije |
| `rollback_plan` | Dokumentirani povratak |
| `approval_ref` | Referenca na izričiti GO |

Bez odgovarajućeg manifesta nema produkcijskog releasea.

### 6. Feature Flags i Kill Switch

Prema ADR-090 i ADR-091 funkcije se kontroliraju iz centralnih postavki.

Predlažem sljedeće skupine:

| Skupina | Primjeri |
|---|---|
| Core UI | Unified Inbox, PWA |
| Mail Operations | Bulk akcije, napredne IMAP funkcije |
| Composer | Scheduled Send, napredni privitci |
| Integrations | Nextcloud, webhookovi |
| AI | OpenAI/Gemini opt-in |
| Security | Sigurnosni blokatori i prisilni režimi |
| Admin | Određene privilegirane funkcije |

Feature flag nije samostalna sigurnosna granica: backend mora provjeravati stvarne ovlasti bez obzira na vidljivost UI funkcije.

Kritični sigurnosni Kill Switch mora moći odmah blokirati rizičnu funkciju, ali ne smije potajno izvršavati produkcijski deployment ili migracije.

### 7. Pravila za agente

Zadržavamo jasnu podjelu odgovornosti.

| Agent | Primarna odgovornost |
|---|---|
| Claude Code | Implementacija i promjene koda |
| GitHub Copilot | GitHub workflow, PR i merge postupci uz GO |
| Codex | Neovisni pregled, sigurnosna i arhitekturna analiza |

Nijedan agent ne dobiva trajno ili opće dopuštenje za produkciju.

Ako je odobreno pisanje koda, to ne znači da je odobren merge. Ako je odobren merge, to ne znači da je odobren deployment.

### 9. Siguran rollback

Predlažem tri vrste povratka:

| Vrsta | Postupak |
|---|---|
| Frontend rollback | Povratak prethodne kompatibilne UI verzije |
| Backend rollback | Povratak prethodnog kompatibilnog API/Worker releasea |
| Database recovery | Zaseban kontrolirani PITR/DR postupak |

Povratak baze nije rutinska zamjena za rollback aplikacije.

Posebno ne smijemo izgubiti nove `send_operation_id`, nacrte ili audit zapise samo zato što prethodna aplikacijska verzija nije kompatibilna.

### 10. Hitne sigurnosne zakrpe

Predlažem mogućnost ubrzanog postupka za kritične sigurnosne probleme.

Ali ni hitan slučaj ne znači automatski deployment bez odobrenja.

Ubrzani postupak može skratiti administrativne korake i ograničiti testni opseg uz dokumentiran rizik, ali mora zadržati minimalne sigurnosne provjere, identitet odobravatelja, audit i izričiti GO.
