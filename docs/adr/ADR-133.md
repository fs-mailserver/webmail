### 2. Glavne API rute

Predlažem sljedeću organizaciju.

| Metoda | Ruta | Funkcija |
|---|---|---|
| `GET` | `/api/v1/mailboxes` | Popis dopuštenih mailboxa |
| `GET` | `/api/v1/mailboxes/{id}/folders` | Mape mailboxa |
| `GET` | `/api/v1/folders/{id}/messages` | Popis poruka |
| `GET` | `/api/v1/messages/{id}` | Detalji poruke |
| `GET` | `/api/v1/search/messages` | Pretraga dopuštenih poruka |
| `POST` | `/api/v1/messages/operations` | Premještanje, zastavice i brisanje |
| `GET` | `/api/v1/messages/operations/{id}` | Status operacije |
| `POST` | `/api/v1/drafts` | Novi nacrt |
| `PATCH` | `/api/v1/drafts/{id}` | Ažuriranje nacrta |
| `POST` | `/api/v1/drafts/{id}/send` | Zahtjev za slanje |
| `GET` | `/api/v1/send-operations/{id}` | Status slanja |
| `POST` | `/api/v1/attachments/uploads` | Sigurni upload privitka |

Ovo je predloženi vanjski ugovor. Konačan popis ruta i shema nastat će kroz OpenAPI specifikaciju prije implementacije.

### 3. Identifikatori u API-ju

Ne želimo da frontend konstruira IMAP identitet iz naziva mapa ili UID vrijednosti.

Predlažem da koristi stabilne, neprozirne identifikatore:

- `mailbox_id`
- `folder_id`
- `message_ref`
- `draft_id`
- `operation_id`
- `send_operation_id`

Backend interno povezuje `message_ref` s mailboxom, mapom, UIDVALIDITY i UID vrijednošću.

**Neprozirni identifikator nije autorizacija.** Svaki zahtjev mora ponovno proći provjeru korisničkih prava.

### 4. Standard odgovora

Predlažem dosljedan format za poslovne operacije.

Primjer odgovora nakon premještanja poruke:

```json
{
  "operation_id": "op_example",
  "status": "pending",
  "resource": {
    "message_ref": "msg_example"
  }
}
```

Korisnik zatim može provjeriti status operacije.

Nećemo tvrditi da je poruka premještena prije nego što je rezultat potvrđen u Dovecotu.

### 5. Autorizacija po endpointu

| API operacija | Obvezna provjera |
|---|---|
| Popis mailboxa | Pristup korisnika i aktivni grantovi |
| Čitanje poruke | `read` |
| Pretraga | `read` za svaki uključeni mailbox |
| Promjena zastavica | `manage_flags` |
| Premještanje | `move` i dopušteno odredište |
| Brisanje | `delete` + dodatna pravila |
| Slanje | `send` + provjeren pošiljateljski identitet |
| Upload privitka | Pravo uređivanja pripadajućeg nacrta |
| Administracija | RBAC + opseg administracije |

Administratorska uloga ne daje automatsko pravo čitanja sadržaja korisničke pošte.

### 6. Idempotencija i konkurentne promjene

Za promjene stanja predlažem:

| Kontrola | Primjena |
|---|---|
| `Idempotency-Key` | Slanje i operacije nad porukama |
| `If-Match` / verzija | Ažuriranje nacrta |
| `operation_id` | Praćenje trajne operacije |
| `request_id` | Dijagnostika |
| `correlation_id` | Povezivanje događaja |
| Keyset cursor | Paginacija poruka |
| Rate limiting | Po korisniku i vrsti operacije |

Idempotency-Key mora biti vezan uz korisnika, dopušteni opseg, vrstu akcije i sadržaj zahtjeva. Ponovna uporaba istog ključa s drugim sadržajem mora proizvesti kontroliranu pogrešku.

### 7. API pogreške

Predlažem standardizirani prikaz u skladu s konceptom Problem Details.

| HTTP status | Primjer |
|---|---|
| `400` | Neispravni parametri |
| `401` | Nije prijavljen |
| `403` | Nedovoljna prava |
| `404` | Nedostupna ili nepostojeća poruka |
| `409` | Konflikt nacrta ili stanja |
| `413` | Poruka ili upload prevelik |
| `422` | Nevaljani poslovni podaci |
| `429` | Prekoračena kvota |
| `503` | Privremeno nedostupna usluga |

Ne smijemo kroz poruke pogrešaka otkriti postojanje nedopuštenih mailboxa, korisničke tajne ili interne putanje servera.

### 8. WebSocket i obavijesti

Prema ADR-013 i ADR-021 koristimo `/ws` za događaje poput:

| Događaj | Svrha |
|---|---|
| `mail.message.created` | Nova poruka |
| `mail.flags.changed` | Promjena pročitanog/oznake |
| `mail.operation.updated` | Status IMAP operacije |
| `mail.sync.updated` | Stanje sinkronizacije |
| `composer.draft.updated` | Promjena nacrta |
| `composer.send.updated` | Status slanja |

WebSocket događaji ne moraju sadržavati puni tekst poruka. Često je dovoljno poslati referencu i minimalne metapodatke te zatim dohvatiti ažurirano stanje autoriziranim API zahtjevom.

Nakon opoziva mailbox prava treba prekinuti ili ograničiti odgovarajuće pretplate na događaje.

### 9. Testiranje API ugovora

Predlažem da svaki endpoint mora imati:

- OpenAPI definiciju.
- Pozitivne i negativne autorizacijske testove.
- Testove idempotencije i konflikata.
- Testove prekida IMAP/SMTP veze.
- Validaciju odgovora.
- Generirani TypeScript klijent.
- Provjeru kompatibilnosti pri promjenama.

Izmjene API ugovora koje lome postojeće klijente zahtijevaju zasebno verzioniranje ili planirani prijelaz.
