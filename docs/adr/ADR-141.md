## Korak 141 — ADR-141: Monitoring, logovi, audit i operativna dijagnostika Webmail Core platforme

Sada detaljno projektiramo **Webmail Core Observability & Operations Center**.

Već smo potvrdili Prometheus, Grafanu, Loki i OpenTelemetry u ADR-026, kao i sigurnosni audit u ADR-067.

Ovdje definiramo kako ih povezati s našim FastAPI, Next.js, Celery, PostgreSQL i mailserver komponentama.

Glavni cilj: **kvar Webmaila mora biti vidljiv i dijagnosticiran, ali prikupljanje telemetrije ne smije ugroziti privatnost korisničke pošte niti rad Postfixa i Dovecota.**

### 4. Privatnost i redakcija logova

Predlažem strogi allowlist pristup: bilježimo samo unaprijed definirana sigurna polja.

| Dopušteno | Zabranjeno u operativnim logovima |
|---|---|
| Vrsta operacije | Tijelo e-maila |
| Status i trajanje | Subject i potpuni primatelji |
| Sanitizirana vrsta pogreške | Lozinke i pristupni tokeni |
| Slučajni correlation ID | Sadržaj privitaka |
| Naziv servisa | Recovery kodovi i MFA tajne |
| Klasifikacija opterećenja | Puni URL-ovi s privatnim parametrima |

Ako se slučajno pojave osjetljivi podaci, pipeline mora pokušati spriječiti njihovu pohranu, a incident treba biti zasebno evidentiran.

Za Prometheus oznake koristimo vrijednosti male kardinalnosti. Ne koristimo `message_ref`, e-mail adrese ili `operation_id` kao metričke labele.

### 5. Audit arhitektura

Prema ADR-067 sigurnosni audit mora imati hash-chain integritet i odvojenu offsite pohranu.

Predlažem sljedeće kategorije:

| Kategorija | Primjeri |
|---|---|
| Authentication | Login, MFA, recovery |
| Authorization | Dodjela i opoziv prava |
| Credential Security | Rotacija i promjene pristupa |
| Mail Operations | Osjetljivo brisanje i delegiranje |
| Admin Operations | Domene, mailboxi, aliasi |
| Queue Management | Flush, hold, release, remove |
| Security Incidents | Blokade, sumnjivi pokušaji |
| Break-glass | Pristup, odobrenje, završetak |

Audit treba imati stabilan identitet aktera, vrijeme događaja, vrstu akcije, referencu na resurs i rezultat.

Izmjene ili brisanje audit zapisa nisu dopuštene običnim aplikacijskim korisnicima.

### 7. Retencija podataka

Usklađujemo se s ADR-067.

| Vrsta | Retencija |
|---|---|
| Operativni logovi | 30 dana |
| Sigurnosni audit | 12 mjeseci |
| Break-glass i kritični audit | 24 mjeseca |
| Metrike | Zasebna politika prema kapacitetu i svrsi |
| Backup | Prema ADR-019 i ADR-073 |

Za metrike predlažem zasebnu politiku, jer čuvanje sirovih visokofrekventnih podataka nije isto što i čuvanje dugoročnih agregata.

### 8. Korelacija incidenta

Sustav treba omogućiti povezivanje:

`request_id → operation_id → worker_job_id → correlation_id`

Na taj način administrator može pratiti problem od korisničke akcije do backend workera, bez potrebe za čitanjem privatnog sadržaja poruke.

Primjerice, možemo utvrditi da je SMTP pokušaj završio kao `unknown` zbog prekida veze, ali time ne dokazujemo je li primatelj dobio poruku.

### 9. Operativna dijagnostika

Predlažem centralni prikaz za:

- Zdravlje svih Webmail servisa.
- IMAP zaostatke po agregiranim kategorijama.
- PostgreSQL stanje i migracije.
- SMTP i Postfix Queue upozorenja.
- Pogreške Credential Brokera.
- Stanje antivirusnih workera.
- Neuspjele administrativne operacije.
- Trenutačne zaštitne režime opterećenja.

Svi dijagnostički endpointi moraju zahtijevati odgovarajuću administratorsku autorizaciju.

### 10. Granice implementacije

**Paket 1:** osnovni healthchecks, strukturirani logovi, minimalni audit i sigurni metrički temelji.

**Paket 4:** potpuni Operations Center, dashboardi, alerting i administrativna dijagnostika.

**Paket 5:** operativni acceptance testovi, simulacije kvarova i provjera retencije.
