Sada moramo definirati **kako ćemo dokazati da novi Webmail radi ispravno i sigurno prije zamjene SnappyMaila**.

### 2. Razine testiranja

| Vrsta testa | Što provjeravamo |
|---|---|
| Unit | Poslovna logika, autorizacija, validacija |
| Integration | FastAPI, PostgreSQL, Redis, IMAP i SMTP |
| Contract | OpenAPI ugovori i TypeScript klijent |
| E2E | Stvarni korisnički tijekovi u pregledniku |
| Security | RBAC, MFA, XSS, CSRF, curenje podataka |
| Resilience | Prekidi mreže, pad workera, restart servisa |
| Performance | Veliki mailboxi, FTS, paralelni korisnici |
| Accessibility | WCAG 2.2 AA i navigacija tipkovnicom |
| Localization | Hrvatski, engleski, španjolski, njemački, talijanski i portugalski |
| Disaster Recovery | Backup, restore, RPO/RTO i recovery mode |

Za implementaciju predlažem pytest za Python, Playwright za E2E te odgovarajuće TypeScript testove. Alate ćemo konačno uskladiti s repozitorijem tijekom tehničke revizije.

### 4. Testna infrastruktura

Prema ADR-072 i ADR-123 koristimo zasebne testne resurse.

| Okruženje | Namjena | Produkcijski podaci |
|---|---|---|
| Local Dev | Razvoj i unit testovi | Zabranjeni |
| CI | Automatizirani testovi | Zabranjeni |
| Staging | Integracija s testnim mailserverom | Zabranjeni |
| Pilot | Kontrolirano korisničko prihvaćanje | Samo zasebno odobreni pristup |
| Production | Stvarni rad nakon cutover GO | Prema produkcijskim pravilima |

Staging može koristiti dogovoreni Docker Compose projekt, ali mora imati odvojene baze, volumene, mreže i testne mailboxe.

### 5. Kriteriji prolaska pojedinog paketa

| Paket | Acceptance Gate |
|---|---|
| 1 — Foundation & Security | Identitet, RBAC, migracije, izolacija, sigurnosni temelji |
| 2 — IMAP Sync | UIDVALIDITY, checkpointi, reconciliation, FTS i bez gubitka poruka |
| 3 — Inbox & Composer | IMAP operacije, nacrti, SMTP, Sent, privitci i frontend |
| 4 — Admin & Operations | Mail Admin Agent, Postfix Queue, monitoring, audit i backup |
| 5 — Hardening & Acceptance | Cjelokupni E2E, sigurnosni, DR, i18n, WCAG i pilot testovi |

Svaki paket ima vlastiti acceptance zapis. Uspjeh prethodnog paketa ne znači automatsko odobrenje sljedećeg.

### 6. Testiranje performansi

Predlažem definirati reprezentativne testne profile, a ne odmah zaključati proizvoljne ciljeve latencije.

| Profil | Scenarij |
|---|---|
| Mali | Jedan mailbox, nekoliko tisuća poruka |
| Srednji | Više mailboxa, deseci tisuća poruka |
| Veliki | Veliki mailboxi, stotine tisuća poruka |
| Paralelni | Istodobni korisnici, sync i pretraga |
| Oporavak | Restart i ponovna sinkronizacija |

Za svaki profil mjerimo API latenciju, IMAP zaostatak, PostgreSQL opterećenje, CPU, RAM i diskovni I/O.

**Postfix i Dovecot moraju ostati operativno zaštićeni.** Veća brzina pretrage nije prihvatljiva ako ugrožava dostavu pošte.

### 7. Upravljanje pronađenim problemima

Predlažem četiri kategorije nalaza.

| Ozbiljnost | Primjer | Odluka |
|---|---|---|
| Critical | Neovlašten pristup mailboxu | Blokira acceptance |
| High | Mogući gubitak ili dvostruko slanje | Blokira acceptance |
| Medium | Neispravan prikaz ili neobičan rubni slučaj | Procjena rizika i korekcija |
| Low | Manji vizualni ili nekritični problem | Može u backlog ako ne krši obvezne kriterije |

Poznati problemi moraju biti dokumentirani. Nema tihog prihvaćanja sigurnosnih iznimaka.
