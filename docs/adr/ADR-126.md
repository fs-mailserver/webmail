## Korak 126 — ADR-126: Model korisnika, autentifikacije, sesija i mailbox ovlasti

Sada projektiramo **Identity & Access Data Model**, temelj sigurnosti cijelog Webmail sustava.

Glavni princip: **jedan Webmail korisnik može upravljati s više mailboxa, ali korisnički identitet, autentifikacija i pristup pošti moraju ostati odvojeni.**

Webmail autentifikacija ne zamjenjuje Dovecot autentifikaciju. Mailbox pristup mora koristiti zasebno kontrolirane IMAP vjerodajnice ili drugi podržan mehanizam pristupa.

### 2. Model korisnika i autentifikacije

Predlažem ove osnovne tablice:

| Tablica | Namjena |
|---|---|
| `identity.users` | Stabilni korisnički identitet |
| `identity.login_identifiers` | E-mail ili drugi identifikator prijave |
| `identity.password_credentials` | Argon2id verifikatori |
| `identity.passkeys` | WebAuthn vjerodajnice i javni ključevi |
| `identity.totp_factors` | TOTP konfiguracija i status |
| `identity.recovery_codes` | Jednokratni kodovi za oporavak |
| `identity.sessions` | Aktivne i opozvane sesije |
| `identity.security_devices` | Registrirani uređaji i povjerenje |

Ovo razdvajanje omogućuje da jedan korisnik ima više načina autentifikacije bez dupliciranja korisničkog računa.

**Passkey je preferirani način prijave**, dok lozinka uz MFA ostaje alternativni postupak prema ADR-064.

TOTP tajne moraju biti šifrirane, a recovery kodovi spremljeni kao sigurni verifikatori, ne kao čitljivi kodovi.

### 3. Korisnički statusi

Predlažem sljedeće statuse identiteta:

| Status | Značenje |
|---|---|
| `invited` | Pozivnica poslana, račun nije aktiviran |
| `active` | Korisnik može pristupiti dopuštenim modulima |
| `suspended` | Privremeno blokiran pristup |
| `offboarded` | Korisnik je uklonjen iz aktivnog korištenja |
| `disabled` | Račun administrativno deaktiviran |

Za osjetljive statusne promjene moramo evidentirati tko ih je pokrenuo, kada i na temelju kojeg dopuštenja.

Brisanje ili deaktivacija Webmail korisnika ne znači automatsko brisanje njegovog Dovecot mailboxa.

### 4. Model mailbox prava

Predlažem da `access.mailbox_grants` koristi dozvole definirane kao zasebne operacije.

| Dozvola | Značenje |
|---|---|
| `read` | Čitanje poruka |
| `send` | Slanje s dopuštenog identiteta |
| `manage_flags` | Pročitano, označeno i slična IMAP stanja |
| `move` | Premještanje poruka |
| `delete` | Brisanje prema dopuštenoj politici |
| `manage_folders` | Upravljanje mapama |
| `manage_rules` | Upravljanje Sieve pravilima |
| `delegate` | Dodjeljivanje dopuštenih prava uz dodatne kontrole |

**Pravo `read` ne daje automatski pravo `send`.**

To je posebno važno za zajedničke mailboxe i asistente koji imaju pristup korespondenciji, ali ne smiju slati e-mailove u ime vlasnika.

### 6. Role i mailbox prava nisu isto

Već imamo tri sistemske uloge:

- **Super Admin**
- **Admin**
- **User**

One određuju administrativne funkcije, ali ne daju automatsko pravo čitanja korisničke pošte.

Predlažem sljedeći podatkovni model:

| Tablica | Svrha |
|---|---|
| `access.role_assignments` | Administrativne uloge i opseg |
| `access.mailbox_grants` | Konkretna mailbox prava |
| `access.delegations` | Privremena delegiranja |
| `access.authorization_events` | Evidencija promjena ovlasti |

Za delegiranje koristimo pravila iz ADR-066, uključujući ograničeno trajanje i zasebne kontrole za posebno osjetljive operacije.

### 7. Sigurne sesije i uređaji

Predlažem server-side sesije s rotacijom identifikatora, zaštitom od session fixation napada i mogućnošću opoziva po uređaju.

| Kontrola | Pravilo |
|---|---|
| Session cookie | `HttpOnly`, `Secure`, odgovarajući `SameSite` |
| CSRF | Obvezna zaštita za promjene stanja |
| Session rotation | Nakon autentifikacije i važnih sigurnosnih promjena |
| Device Manager | Pregled i opoziv sesija |
| Admin MFA | Obvezan |
| Security events | Prijave, neuspjesi, opozivi i promjene vjerodajnica |
| Recovery | Kontrolirani postupak bez zaobilaženja MFA pravila |

Detaljni vremenski limiti sesija i politika ponovne autentifikacije mogu biti konfigurabilni, ali ne smiju biti proizvoljni u pojedinim modulima.

### 8. Ključno pitanje — kako povezati Webmail korisnika i mailbox?

Postoje dva arhitekturna modela.

**Model A:** Webmail korisnik postoji neovisno o mailboxu. Administrator dodjeljuje mailbox, a korisnik zasebno potvrđuje pristup prema ADR-083.

**Model B:** Svaki Webmail korisnik primarno je vezan uz jednu e-mail adresu, dok su dodatni mailboxi prošireni povezani računi.

Model A bolje odgovara našem već potvrđenom sustavu više mailboxa po korisniku i granularnim pravima.
