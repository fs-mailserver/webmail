## Korak 72 — ADR-072: Staging, migracije baze i kontrolirani rollback

Sada definiramo kako ćemo izdavati nove verzije Webmaila bez ugrožavanja postojećeg Docker Mailservera i ostalih aplikacija na dedicated serveru.

Najvažniji cilj je **odvojiti razvoj, testiranje i produkcijsku primjenu**, čak i kada dijele istu fizičku infrastrukturu.

### 2. Razdvajanje okruženja

| Okruženje | Namjena | Podaci |
|---|---|---|
| Development | Programiranje i lokalni testovi | Sintetički podaci |
| CI/Test | Automatski testovi i sigurnosne provjere | Privremena testna baza |
| Staging | Provjera stvarnog release kandidata | Izolirana baza i testni mailboxi |
| Production | Stvarni Webmail i postojeći DMS | Produkcijski podaci |

Staging ne smije dijeliti produkcijske IMAP račune, PostgreSQL shemu, Redis redove, API ključeve ni mogućnost slanja e-mailova stvarnim primateljima.

### 3. Migracije PostgreSQL-a

Koristit ćemo **Alembic** za verzionirane migracije FastAPI/SQLAlchemy baze `webmail_db`.

Predlažem strategiju *expand → migrate → contract*.

| Faza | Postupak |
|---|---|
| Expand | Dodavanje novih tablica i stupaca bez uklanjanja starih |
| Migrate | Postupna migracija podataka, uz provjere |
| Contract | Uklanjanje zastarjele strukture tek u kasnijem izdanju |

Time omogućujemo da stara i nova verzija aplikacije privremeno rade s kompatibilnom shemom.

**Važno:** rollback Docker imagea ne vraća automatski PostgreSQL bazu na prethodno stanje. Destruktivne migracije zahtijevaju poseban postupak oporavka.

### 4. Kontrolirani rollback

Predlažem sljedeća pravila:

- Prije deploya mora postojati provjeren i dovoljno svjež backup.
- Release koristi točno određene Docker image digeste.
- Prije primjene provjeravaju se dostupnost servisa i kapacitet diska.
- Nova verzija mora proći healthcheck i funkcionalni smoke test.
- Ako deploy ne uspije, vraćaju se prethodni kompatibilni imageovi i konfiguracija.
- Ako je promijenjena struktura podataka, koristi se unaprijed odobren migracijski ili restore postupak.
- Postojeći Docker Mailserver ne smije se nepotrebno rekreirati tijekom Webmail deploya.

### 5. Posebna zaštita postojećeg mailservera

Budući da smo u ADR-002 odlučili zadržati Webmail unutar postojećeg `compose.yaml`, sam zajednički Compose projekt ne znači da trebamo pokretati `docker compose up` nad svim servisima.

Deploy treba ciljati samo promijenjene Webmail servise i njihove nužne ovisnosti, bez automatskog ažuriranja ili restartanja Dovecota, Postfixa i ostalih produkcijskih komponenti.
