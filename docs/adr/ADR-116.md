## Korak 116 — ADR-116: Odobravanje automatiziranih radnji i višestupanjski workflowovi

Sada projektiramo **Workflow Approval & Execution Manager**.

ADR-115 definirao je kako korisnik izrađuje automatizaciju. U ovom koraku definiramo kako sustav izvršava složenije procese koji sadrže više koraka i zahtijevaju korisničke potvrde.

Primjerice, kada stigne poslovni e-mail, Webmail može izraditi zadatak, dodijeliti ga odgovornoj osobi i pripremiti nacrt odgovora. Međutim, odgovor se ne smije samostalno poslati.

### 3. Koje radnje zahtijevaju odobrenje?

| Radnja | Predložena politika |
|---|---|
| Kreiranje osobnog zadatka | Automatski po aktivnom pravilu |
| Promjena oznake poruke | Automatski ako je dopušteno pravilom |
| Interni podsjetnik | Automatski |
| Kreiranje nacrta | Automatski, bez slanja |
| Slanje e-maila | Izričito odobrenje |
| RSVP odgovor | Izričito odobrenje |
| Dodjela zadatka drugome | Provjera prava i prethodno odobrenog opsega |
| Dijeljenje Nextcloud datoteke | Izričito odobrenje |
| Brisanje poruka ili datoteka | Posebna potvrda; opasne operacije isključene iz općeg workflowa |
| Promjena ovlasti korisnika | Administrativni postupak iz ADR-085, ne obični workflow |

Workflow ne smije zaobići pravila koja već imamo za Mail Admin Agent, delegiranje ili pristup tuđim mailboxima.

Stvarni Approval Center mora prikazati precizno **što će se izvršiti**, kome, s kojim podacima i s kojim ovlastima.

Ako se sadržaj radnje promijeni nakon odobrenja, odobrenje prestaje vrijediti i mora se ponovno zatražiti.

### 5. Trajni statusi izvršavanja

Svaki workflow dobiva jedinstveni `execution_id`, a svaka operacija zasebni `step_id`.

| Status | Značenje |
|---|---|
| `queued` | Čeka pokretanje |
| `running` | Aktivno izvršavanje |
| `waiting_approval` | Čeka korisničku potvrdu |
| `approved` | Odobrena je točno određena verzija radnje |
| `rejected` | Odbijeno |
| `completed` | Uspješno završeno |
| `failed` | Greška uz evidentiran razlog |
| `cancelled` | Zaustavljeno |
| `expired` | Odobrenje ili workflow više nije valjan |

Zahtjev za odobrenje mora biti jednokratan i vezan uz korisnika, verziju workflowa te točan sadržaj predložene akcije.

### 6. Što se događa nakon prekida servera?

Prema postojećoj arhitekturi, PostgreSQL trajno pohranjuje stanje workflowa.

Nakon restarta worker može nastaviti sigurno ponovljive korake. Za radnje s vanjskim učinkom — osobito SMTP slanje — potreban je oprezniji postupak.

Ako sustav ne može pouzdano utvrditi je li poruka već poslana, **ne smije je automatski ponovno poslati**. Takav korak prelazi u stanje za provjeru i eventualnu ručnu intervenciju.

Također predlažem ograničeno trajanje odobrenja, primjerice 24 sata kao početnu vrijednost, uz mogućnost konfiguracije prema osjetljivosti radnje.

### 7. Više osoba u postupku odobravanja

Za uobičajene korisničke workflowove dovoljan je jedan ovlašteni korisnik.

Za posebno osjetljive operacije možemo zahtijevati **dvije različite osobe**, primjerice predlagatelja i odobravatelja. To se povezuje s pravilima iz ADR-066 i ADR-086, ali ne zamjenjuje njihove sigurnosne kontrole.

Odobrenje jednog korisnika ne smije biti dovoljno ako postojeća administrativna politika zahtijeva neovisnog drugog odobravatelja.
