## Korak 70 — ADR-070: Sigurnost Docker kontejnera, mrežna izolacija i zaštita produkcijskog servera

Sada definiramo sigurnosna pravila za pokretanje novog Webmaila na postojećem dedicated serveru.

Već smo usvojili:

- **ADR-002:** Webmail se integrira u postojeći `/opt/stacks/mailserver/compose.yaml`.
- **ADR-003:** privilegirane operacije izvršava zaseban Mail Admin Agent.
- **ADR-021:** javni pristup ide preko Traefika, dok interni servisi ostaju izolirani.
- **ADR-069:** tajne i kriptografski ključevi imaju zasebnu zaštitu.

Naš cilj je da eventualna kompromitacija Next.js aplikacije ne omogući automatski pristup Dovecotu, PostgreSQL-u, Docker hostu ili drugim aplikacijama na serveru.

### 2. Sigurnosna pravila za kontejnere

| Kontrola | Predložena politika |
|---|---|
| Root korisnik | Non-root gdje god je moguće |
| Linux capabilities | `cap_drop: ALL`, dodati samo nužne |
| Privilegirani način rada | Zabranjen prema zadanim postavkama |
| Datotečni sustav | `read_only: true` gdje servis dopušta |
| Privremene datoteke | Ograničeni `tmpfs` volumeni |
| Docker socket | Zabranjen za Next.js, FastAPI i obične workere |
| Docker mreže | Odvojene mreže i najmanje potrebne veze |
| Tajne | Preko odobrenog Secrets Managera |
| Resursi | CPU, RAM i procesna ograničenja po servisu |
| Healthcheck | Obvezan za ključne servise |
| Image verzije | Kontrolirane verzije i digesti |
| Skeniranje | Provjera ranjivosti prije odobrenja izdanja |

Za postojeći Docker Mailserver nećemo slijepo nametati `cap_drop: ALL` ili `read_only: true`, jer to može onemogućiti rad Postfixa ili Dovecota. Svaku izmjenu moramo testirati.

### 3. Posebna zaštita Mail Admin Agenta

Mail Admin Agent je najosjetljivija komponenta jer može upravljati mailboxima, domenama i konfiguracijom mailservera.

Predlažem sljedeće:

- Nema javno izloženih portova.
- Prihvaća samo unaprijed definirane administrativne operacije.
- Svaki zahtjev mora biti autentificiran i autoriziran.
- Ne prihvaća proizvoljne shell naredbe.
- Ne dobiva puni Docker socket ako se operacije mogu izvesti preko užeg sučelja.
- Promjene konfiguracije prolaze validaciju, audit i kontrolirani rollback.

**Važno:** sama Docker mrežna izolacija nije dovoljna zaštita ako kompromitirani servis posjeduje privilegirane vjerodajnice ili pristup datotekama hosta.

### 4. Zaštita dedicated servera

Na razini Ubuntu hosta predlažem sljedeće kontrole:

| Područje | Zaštita |
|---|---|
| SSH | Ključevi, ograničen pristup, bez root prijave lozinkom |
| Firewall | Samo nužni javni portovi |
| Docker daemon | Bez javnog TCP pristupa |
| Sistemske nadogradnje | Kontrolirano sigurnosno ažuriranje |
| AppArmor | Profiliranje osjetljivih servisa gdje je izvedivo |
| Fail2ban / ekvivalent | Zaštita autentifikacijskih servisa |
| Audit | Evidencija privilegiranih promjena |
| Backup | Odvojen, šifriran i provjerljivo obnovljiv |

Moramo paziti da firewall politika ne prekine postojeće SMTP, Submission, IMAPS i druge mail protokole.

### 5. Strategija promjena

Imamo produkcijski mailserver koji već radi. Zato predlažem da uvođenje sigurnosnih ograničenja bude postupno.

Prvo ćemo u izoliranom testnom okruženju provjeriti sigurnosne postavke svakog novog kontejnera. Tek nakon zasebnog odobrenja mogu se primijeniti na produkciju.

Nećemo automatski mijenjati postojeće Docker mreže ili mountove drugih aplikacija.
