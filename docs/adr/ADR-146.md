### 2. Pet implementacijskih paketa

| Paket | Sadržaj | Ovisnost |
|---|---|---|
| **1 — Foundation** | Monorepo, konfiguracija, identitet, sigurnost, osnovni API, migracije | Nema |
| **2 — Mail Sync** | IMAP, UIDVALIDITY, checkpointi, FTS indeks | Paket 1 |
| **3 — Inbox & Composer** | Next.js Inbox, nacrti, SMTP, Sent, privitci | Paketi 1–2 |
| **4 — Admin & Operations** | Domene, mailboxi, queue, audit, monitoring | Paketi 1–3 |
| **5 — Hardening** | E2E, sigurnost, DR, WCAG, pilot acceptance | Svi prethodni |

Svaki paket zadržava zaseban implementacijski GO i zasebno prihvaćanje.

### 3. Arhitekturna kontrola ovisnosti

Prije početka razvoja trebamo eksplicitno provjeriti nekoliko osjetljivih područja.

| Područje | Što još treba potvrditi tehničkom provjerom |
|---|---|
| Dovecot 2.4 | Točno ponašanje IMAP funkcija, QRESYNC/CONDSTORE i autentifikacije |
| SMTP | Način autoriziranog slanja i korelacije s Postfix queueom |
| Credential Broker | Stvarni način pristupa IMAP/SMTP računima bez izlaganja tajni |
| PostgreSQL | FTS jezici, migracije, indeksiranje, kapacitet |
| Docker | Mrežna izolacija, privilegije Agenta, Compose kompatibilnost |
| Traefik | Siguran routing `/api` i `/ws`, cookieji i TLS |
| Backup | Konzistentnost baze i datoteka, dostupnost recovery ključeva |
| SnappyMail | Povratak na postojeći klijent bez nepotrebnih promjena mailboxa |

Ovdje razlikujemo **arhitekturnu odluku** od **tehnički provjerene mogućnosti**. To što smo nešto definirali u ADR-u ne dokazuje da postojeći mailserver podržava upravo taj način rada.

Predlažem pripremiti jedan **Architecture Baseline v1.0** s:

- dijagramom komponenti i granica povjerenja;
