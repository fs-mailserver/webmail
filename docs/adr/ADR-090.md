## Korak 90 — ADR-090: Centralna konfiguracija i Feature Flags

Sada definiramo **Configuration & Feature Management Service**, sustav kojim ćemo upravljati postavkama i uključivanjem novih funkcionalnosti Webmaila.

To je posebno važno jer razvijamo velik sustav s brojnim modulima: AI, kalendar, kontakti, arhiva, webhookovi, administracija i mobilne obavijesti.

Želimo moći uključiti ili isključiti pojedinu funkcionalnost **bez ponovnog buildanja Next.js aplikacije i bez restartanja Dovecota ili Postfixa**.

PostgreSQL ostaje autoritativan za aplikacijsku konfiguraciju, dok Redis služi za brzu distribuciju promjena. Kriptografske tajne ostaju u zasebnom Secrets Manageru iz ADR-069.

### 2. Razine konfiguracije

Predlažem sljedeću hijerarhiju:

| Razina | Primjeri |
|---|---|
| Globalna | Omogućavanje AI modula, integracija i novih funkcija |
| Domena | Zadana mailbox kvota, dopuštene integracije |
| Mailbox | AI opt-in, pravila sinkronizacije |
| Korisnik | Tema, jezik, prečaci, obavijesti |
| Servis | Worker concurrency, timeout, limiti |

Vrijednosti se nasljeđuju samo ondje gdje je to izričito dopušteno. Sigurnosne zabrane i izričiti korisnički zahtjevi za privatnošću ne smiju se zaobići postavkom više razine.

Primjerice, globalno omogućavanje AI modula **ne smije automatski uključiti AI obradu privatnih mailboxa**. Za to i dalje vrijedi per-mailbox opt-in iz ADR-015.

### 4. Sigurnost konfiguracije

Nisu sve postavke jednako osjetljive.

| Vrsta promjene | Politika |
|---|---|
| Tema i jezik | Korisnik mijenja sam |
| Korisničke obavijesti | Korisnik mijenja sam |
| Uključivanje nove AI funkcije | Admin autorizacija + poštovanje opt-in pravila |
| Promjena worker limita | Ovlašteni administrator |
| Sigurnosna politika | Super Admin + kontrolirani workflow |
| SMTP/Dovecot konfiguracija | Mail Admin Agent, zaseban postupak |
| Secrets i kriptografski ključevi | Isključivo Secrets Manager |

Posebno osjetljive promjene ne smiju se izvršavati samo promjenom vrijednosti u PostgreSQL tablici.

### 5. Verzije i rollback konfiguracije

Svaka administrativna promjena dobiva verziju, autora, vrijeme i razlog.

Primjerice, ako nova postavka uzrokuje probleme s IMAP sinkronizacijom, administrator može vratiti prethodnu kompatibilnu konfiguraciju.

Za taj postupak predlažem:

- Validaciju nove konfiguracije prije aktivacije.
- Atomsku objavu nove verzije za pripadajući skup postavki.
- Evidenciju aktivne i prethodne verzije.
- Automatsku distribuciju promjene servisima.
- Povratak na prethodnu dopuštenu verziju nakon autorizacije.

**Važno:** rollback konfiguracije ne poništava već izvršene poslovne operacije, poput poslanih e-mailova ili promijenjenih mailbox prava.

### 6. Što ako Redis ili konfiguracijski servis nije dostupan?

Predlažem da se servisi za neosjetljive prikazne postavke mogu privremeno osloniti na posljednju provjerenu konfiguraciju.

Za ovlasti, sigurnosne zabrane, opozive pristupa i slične kritične kontrole vrijedi **fail-closed**: ako nije moguće pouzdano utvrditi dopuštenje, osjetljiva operacija neće se izvršiti.
