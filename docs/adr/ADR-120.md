### 3. Kriteriji prihvaćanja

Predlažem da razvoj Workflow podsustava ne može biti prihvaćen dok ne zadovolji sljedeće uvjete.

| Kriterij | Očekivani rezultat |
|---|---|
| Autorizacija | Default-deny i provjera prava pri izvršavanju |
| Dry Run | Bez stvarnih promjena vanjskih sustava |
| Idempotencija | Nema ponavljanja logički iste akcije |
| SMTP recovery | Neizvjesno slanje ide na ručnu provjeru |
| Approval | Odobrenje vrijedi samo za konkretnu verziju akcije |
| Audit | Svaka osjetljiva operacija ima zapis |
| Resursi | Workflow poštuje definirane kvote |
| Kill Switch | Zaustavlja nova nedopuštena izvršavanja |
| Privatnost | Logovi ne otkrivaju sadržaj poruka |
| Oporavak | Restart ne gubi trajno stanje poslova |
| Testovi | Unit, integration, security i E2E |
| Produkcija | Samo nakon zasebnog GO |

### 5. Posebno pitanje: kada smatramo arhitekturu spremnom?

Ovdje bih jasno razdvojio tri stanja:

| Stanje | Značenje |
|---|---|
| **Architecture Defined** | Potvrdili smo projektne odluke |
| **Architecture Reviewed** | Provjereni su sukobi, sigurnost, ovisnosti i otvorena pitanja |
| **Implementation Approved** | Dobili smo zaseban GO za konkretan razvojni zadatak |

Trenutačno smo u prvoj fazi za ovaj podsustav. ADR-120 može definirati obveznu drugu fazu, ali sam po sebi ne daje GO za implementaciju.

### 6. Predloženi način pripreme razvoja

Nakon stvarne revizije mogli bismo sastaviti:

- Tehnički ADR dokument s evidencijom potvrđenih odluka.
- API ugovore i PostgreSQL model podataka.
- Popis sigurnosnih invarianti.
- Testne scenarije i acceptance kriterije.
- Razvojne zadatke za Claude Code.
- Odvojene GitHub/PR zadatke za Copilot agenta.

To bi bio prijelaz iz projektiranja u pripremu implementacije, ali još uvijek bez produkcijskih izmjena.
