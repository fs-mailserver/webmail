## Korak 123 — ADR-123: Redoslijed razvoja Webmail Core modula i granice prvog implementacijskog paketa

Sada moramo definirati **kojim redoslijedom ćemo razvijati Webmail Core**, tako da pojedini moduli imaju jasne ovisnosti i da se ništa ne mijenja na produkcijskom mailserveru prije odobrenja.

Predlažem razvoj u manjim paketima, pri čemu svaki paket ima vlastite testove i kriterije prihvaćanja.

### 2. Ovisnosti i kriteriji

| Paket | Glavna isporuka | Uvjet prihvaćanja |
|---|---|---|
| 1 — Foundation | Izolirano razvojno okruženje, API kostur, DB migracije, osnovni auth/RBAC | Testirane sigurnosne granice i migracije |
| 2 — IMAP | Sigurna sinkronizacija i indeksiranje testnih mailboxa | Bez gubitka poruka i curenja podataka |
| 3 — Mail UI | Inbox, Composer, IMAP/SMTP tijekovi | Ispravni nacrti, Sent i zaštita od duplog slanja |
| 4 — Operations | Administracija, audit, backup i monitoring | Kontrolirane administrativne operacije i test obnove |
| 5 — Acceptance | Cjelovita Core aplikacija | Testovi, sigurnosna revizija i provjeren rollback |

**Bitna dopuna:** sigurnost, audit, osnovna telemetrija, lokalizacija i pristupačnost počinju već u Paketu 1 i razvijaju se kroz sve pakete. Ne smijemo ih tek na kraju dodavati u gotovu aplikaciju.

### 4. Potrebna izolacija

Raniji ADR-072 definirao je staging u okviru istog Docker Compose projekta, uz zasebne servise, mreže, volumene i baze.

Kako bismo to uskladili s ADR-027, predlažem:

| Okruženje | Politika |
|---|---|
| Local Dev | Samostalni testni Compose stack |
| CI | Izolirane efemerne testne usluge |
| Server Staging | Odvojeni servisi unutar dogovorenog Compose projekta |
| Production | Ne mijenja se bez zasebnog GO |

Staging ne smije koristiti iste PostgreSQL sheme, IMAP korisnike ili datotečne volumene kao produkcija.

### 5. Agenti i GitHub zadaci

Zadržavamo odvojene odgovornosti.

| Agent | Odgovornost |
|---|---|
| **Claude Code** | Implementacija aplikacijskog koda, migracija i testova |
| **Copilot agent** | GitHub struktura, grane, PR-ovi i GitHub administrativni tijekovi |
| **Codex** | Neovisna analiza, tehnička revizija ili dijagnostika prema zadatku |

Nijedan agent ne smije automatski provesti merge ili produkcijski deployment.

### 6. Pravilo za prijelaz između paketa

Predlažem da **GO za jedan paket ne znači GO za sljedeći paket**.

Primjerice, nakon Paketa 1 moramo pregledati kod, migracije, sigurnosne kontrole i testove. Tek nakon prihvaćanja možemo odlučiti hoćemo li pokrenuti Paket 2.

To će nam omogućiti kontrolu nad razvojem, a istodobno zadržati potpunu arhitekturnu dosljednost.
