## Korak 134 — ADR-134: Next.js Inbox, prikaz poruka i sinkronizacija korisničkog sučelja

Sada projektiramo **glavno korisničko sučelje Webmaila**, odnosno dio aplikacije koji će korisnik svakodnevno koristiti umjesto SnappyMaila.

Ostajemo pri ranije potvrđenom rasporedu s tri panela, ali sada moramo definirati kako sučelje radi s više mailboxa, velikim brojem poruka i promjenama koje stižu preko WebSocketa.

### 2. Glavni dijelovi Inboxa

| Dio | Funkcionalnost |
|---|---|
| Sidebar | Mailboxi, mape, favoriti i brojači |
| Message List | Poruke, pošiljatelji, datumi, privitci, zastavice |
| Reading Pane | Sigurno otvaranje MIME/HTML poruke |
| Toolbar | Reply, Forward, Move, Delete, Flag |
| Search | PostgreSQL FTS preko autoriziranog API-ja |
| Status | Sinkronizacija, pogreške, nepotpun indeks |
| Composer | Novi e-mail i uređivanje nacrta |

Napredna četiri Inbox načina iz ADR-098 ostaju za fazu Advanced Mail. Core verzija mora imati izvrstan osnovni prikaz poruka.

### 3. Više mailboxa

Korisnik mora moći jednostavno mijenjati mailbox bez ponovne prijave.

Predlažem da sidebar grupira mailboxe, a svaki mailbox ima vlastite mape i brojače.

Uz to, prema ADR-047 zadržavamo **Unified Inbox** kao jedinstveni pogled na dopuštene poruke. Za Core verziju predlažem barem objedinjeni popis pristigle pošte, dok napredne razgovorne prikaze možemo uvesti kasnije.

Prilikom opoziva prava nad nekim mailboxom, njegove se poruke odmah uklanjaju iz aktivnog korisničkog prikaza i onemogućuje se njihov ponovni dohvat kroz API.

### 4. Prikaz velikog broja poruka

Ne želimo da Webmail učitava desetke tisuća poruka odjednom.

Predlažem:

- Keyset paginaciju preko API-ja.
- Virtualizirani popis poruka.
- Postupno dohvaćanje detalja.
- Cache ograničen korisničkim pravima i stanjem sesije.
- Otkazivanje zastarjelih zahtjeva pri promjeni mailboxa.
- Jasnu oznaku kada indeks još nije potpun.

Paginacija mora imati stabilno sortiranje kako nove poruke ne bi uzrokovale preskakanje ili dupliciranje rezultata.

### 6. Optimistički UI i pogreške

Prema ADR-129, neke radnje možemo odmah vizualno prikazati, primjerice označavanje pročitanog ili premještanje.

Međutim, korisnik mora znati je li promjena:

| Status | Prikaz |
|---|---|
| `pending` | Promjena se izvršava |
| `confirmed` | Dovecot potvrdio |
| `failed` | Prikaži pogrešku i uskladi stanje |
| `unknown` | Prikaži da je potrebna provjera |

Kod trajnog brisanja ne koristimo optimistički prikaz kao zamjenu za potvrdu.

### 7. Sigurno čitanje poruka

Reading Pane mora koristiti MIME i HTML sigurnosna pravila iz ADR-038 i ADR-131.

To uključuje sanitizirani HTML, blokirane udaljene slike prema zadanim postavkama, izolirane privitke i jasna upozorenja na potencijalni phishing.

Prikaz e-maila ne smije omogućiti izvršavanje aktivnog sadržaja ili pristup internim aplikacijskim podacima.

### 9. Upravljanje lokalnim stanjem

Predlažem razliku između:

| Vrsta stanja | Gdje se čuva |
|---|---|
| Poruke i IMAP zastavice | Dovecot |
| Sinkronizirani indeks | PostgreSQL |
| Korisničke UI postavke | PostgreSQL |
| Privremeni frontend cache | Memorija aplikacije |
| Odabrani offline podaci | PWA IndexedDB prema ADR-024 |
| Nacrti | PostgreSQL + IMAP Drafts |

Kod odjave i opoziva uređaja pokrećemo čišćenje dostupnih lokalnih podataka prema ADR-062, uz jasno priznavanje ograničenja već kopiranih offline podataka.
