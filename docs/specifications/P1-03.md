## 2. Model korisničkog identiteta

Predlažem proširiti prethodno definiranu tablicu `identity.users`.

| Polje | Tip | Namjena |
|---|---|---|
| `id` | UUID | Stalni interni identitet |
| `email` | Text | Prijavna adresa |
| `email_verified_at` | timestamptz | Potvrda adrese |
| `display_name` | Text | Prikazano ime |
| `status` | Enum/Text | Invited, active, suspended, disabled |

Primarni ključ je UUID, a prijavna adresa mora imati jedinstvenu kanonsku vrijednost definiranu konzistentnom politikom normalizacije.

Ne pretpostavljamo da je svaka promjena e-mail adrese bezopasna: zahtijeva ponovnu autentifikaciju i provjeru nove adrese.

## 4. Alternativna prijava: lozinka + TOTP

Za korisnike koji ne mogu koristiti Passkey zadržavamo alternativu.

| Element | Pravilo |
|---|---|
| Lozinka | Argon2id hash |
| TOTP | Standardni vremenski ograničeni kod |
| Tajna TOTP-a | Šifrirana ili referenca na Secret Store |
| Rate limiting | Po računu i dodatnim relevantnim signalima |
| Pogreške prijave | Generičke korisničke poruke |
| MFA za administratore | Obvezna |

Lozinke ne smiju biti pohranjene ili zapisane u logovima.

Za TOTP treba spriječiti ponovnu upotrebu već prihvaćenog koda unutar istog vremenskog koraka, uz pažljivo definiranu toleranciju na odstupanje sata.

## 5. Recovery model

Prema ADR-137 koristimo jednokratne recovery kodove.

Predlažem da korisnik kod prvog postavljanja dobije skup kodova koje može sigurno spremiti.

U bazi pohranjujemo samo odgovarajuće verifikatore kodova, a ne njihove čitljive vrijednosti.

Kada korisnik iskoristi recovery kod, označava se kao iskorišten u istoj transakciji kojom se potvrđuje recovery događaj.

Za administratorski recovery vrijedi stroža procedura s neovisnim odobravateljem.

Cookie sadrži nepredvidivi session identifikator, a PostgreSQL čuva samo njegov sigurni verifikator.

Predložene vrijednosti iz ADR-137:

| Parametar | Obični korisnik | Administrator |
|---|---|---|
| Idle timeout | 12 sati | 30 minuta |
| Maksimalno trajanje | 7 dana | 12 sati |
| Step-up valjanost | Najviše 5 minuta | Najviše 5 minuta |
| Revoke | Trenutačno za nove online zahtjeve | Isto |

Session cookie koristimo s `Secure`, `HttpOnly` i odgovarajućom `SameSite` politikom, uz dodatnu CSRF zaštitu.

`last_seen_at` ne treba ažurirati za svaki pojedini zahtjev ako to nepotrebno opterećuje PostgreSQL. Moguće je kontrolirano osvježavanje uz zadržavanje pravilnog obračuna isteka.

## 8. Step-up autentifikacija

Za osjetljive operacije potrebno je potvrditi nedavnu autentifikaciju.

Primjeri su dodavanje novog Passkeya, promjena MFA metode, resetiranje vjerodajnica i privilegirane administrativne operacije.

Step-up dokaz mora biti vezan uz konkretnu sesiju, korisnika i ograničeni vremenski prozor. Za kritične operacije dodatno se provjerava opseg akcije.

Ne smijemo dopustiti da jedna potvrda automatski autorizira neograničen broj različitih kritičnih zahvata.

## 9. API ugovori — predloženi endpointi

| Endpoint | Namjena |
|---|---|
| `POST /api/v1/auth/passkeys/options` | Opcije WebAuthn prijave |
| `POST /api/v1/auth/passkeys/verify` | Provjera prijave |
| `POST /api/v1/auth/password/login` | Lozinka + MFA tijek |
| `POST /api/v1/auth/logout` | Odjava |
| `GET /api/v1/auth/sessions` | Popis sesija |
| `DELETE /api/v1/auth/sessions/{id}` | Opoziv sesije |
| `POST /api/v1/auth/step-up` | Dodatna autentifikacija |
| `POST /api/v1/auth/recovery` | Kontrolirani recovery |

Registracija Passkeya i MFA konfiguracija zahtijevat će zasebne endpointove u istoj API domeni.

Svi endpointi moraju koristiti Pydantic validaciju, zaštitu od automatiziranih napada, centralizirano evidentiranje sigurnosnih događaja i pravilne HTTP statuse.
