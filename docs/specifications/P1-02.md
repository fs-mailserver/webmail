### 2. Plan tablica prema razvojnim paketima

| Shema | Glavne tablice | Paket |
|---|---|---|
| `identity` | `users`, `passkeys`, `mfa_factors`, `recovery_codes`, `sessions` | 1 |
| `access` | `role_assignments`, `mailbox_grants`, `delegations` | 1 |
| `system` | `feature_flags`, `admin_operations`, `schema_metadata` | 1 |
| `audit` | `security_events`, `audit_chain_heads` | 1 |
| `mail` | `mailboxes`, `folders`, `messages`, `sync_checkpoints` | 2 |
| `search` | `message_index`, `attachment_index`, `index_status` | 2 |
| `composer` | `drafts`, `draft_versions`, `send_operations` | 3 |
| `integration` | `connections`, `webhook_subscriptions` | Kasnije faze |

**Napomena:** tablice su predloženi logički model; njihov konačni SQL i relacije trebaju proći zasebni pregled prije implementacije.

### 3. Identity shema

Predlažem sljedeći minimalni skup entiteta:

| Tablica | Ključna polja |
|---|---|
| `identity.users` | `id`, `email`, `status`, `created_at`, `updated_at` |
| `identity.passkeys` | `id`, `user_id`, `credential_id`, `public_key`, `sign_count`, `created_at` |
| `identity.mfa_factors` | `id`, `user_id`, `factor_type`, `secret_ref`, `enabled_at` |
| `identity.recovery_codes` | `id`, `user_id`, `code_hash`, `used_at` |
| `identity.sessions` | `id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `last_seen_at` |

Dodatno pravilo: Passkey `credential_id` mora biti jedinstven, a autentifikacijski ključevi i recovery kodovi ne smiju se spremati u čitljivom obliku.

Ako koristimo alternativnu prijavu lozinkom, ona mora imati zaseban verifikator lozinke (npr. Argon2id hash), a ne polje s čitljivom lozinkom.

### 4. Access shema

Prema ADR-065 i ADR-066, autorizacija je *default deny*.

| Tablica | Namjena |
|---|---|
| `access.role_assignments` | Globalne i domenske uloge |
| `access.mailbox_grants` | Veza korisnika s mailboxom i dozvoljenim akcijama |
| `access.delegations` | Privremeno delegiranje ovlasti |

Važno je ne pretpostaviti da Webmail administrator može čitati tuđu poštu.

Za mailbox grant predlažem skup dopuštenih ovlasti poput `read`, `send`, `manage_flags`, `move`, `delete`, uz odvojenu validaciju stvarne IMAP/SMTP mogućnosti.

### 5. Referenciranje mailboxa prije Paketa 2

U Paketu 1 još ne povezujemo stvarne mailboxe.

Zato predlažem koristiti stabilni interni `mailbox_ref` koji pripada testnom katalogu mailbox identiteta.

Takva referenca omogućuje testiranje RBAC-a bez stvarnog IMAP pristupa.

Pri kasnijem uvođenju `mail.mailboxes`, migracija će povezati odobrene grantove s potvrđenim mailbox zapisima.

**Ne smijemo dozvoliti da proizvoljna adresa koju klijent pošalje automatski postane autorizirani mailbox.**

### 6. Sigurnost baze

Predlažem razdvajanje pristupa na razini PostgreSQL rola.

| Rola | Privilegije |
|---|---|
| `webmail_user` | Samo potrebni aplikacijski DML pristup |
| `webmail_migrator` | Kontrolirani DDL i Alembic migracije |
| `webmail_readonly` | Ograničena dijagnostika, bez tajni |
| Backup identitet | Samo ovlasti potrebne za backup postupak |

Aplikacijski račun ne smije imati `SUPERUSER`, `CREATEDB` ili široke privilegije nad tuđim bazama.

Za pristup tablicama s posebno osjetljivim podacima koristimo dodatne zaštite na razini aplikacije i odgovarajuća ograničenja pristupa.

### 7. Pravila PostgreSQL modeliranja

Predlažem:

| Područje | Pravilo |
|---|---|
| Primarni ključevi | UUID |
| Vrijeme | `timestamptz`, UTC |
| E-mail identitet | Normalizacija uz očuvanje originalne vrijednosti gdje treba |
| Jedinstvenost | Eksplicitni unique constraints |
| Relacije | Foreign keys |
| Brisanje | Bez nekontroliranog `ON DELETE CASCADE` za sigurnosne zapise |
| JSONB | Samo za fleksibilne pomoćne metapodatke |
| Audit | Append-only logički model |
| Tajne | Reference na Secret Store, ne čitljive vrijednosti |
| Migracije | Jedinstvena Alembic povijest |

UUID omogućuje stabilne interne identifikatore, ali javni API i dalje mora koristiti autorizirane, nepredvidive reference.

### 8. Alembic migracijski model

Predlažem centralni Alembic direktorij iz P1-01:

`migrations/`

Migracije moraju biti:

- Verzijski kontrolirane.
- Testirane na praznoj bazi.
- Testirane na prethodnoj kompatibilnoj verziji.
- Bez proizvoljnog automatskog izvršavanja pri pokretanju API-ja.
- Izvedene isključivo uz zasebno odobrenje u odgovarajućem okruženju.
- Kompatibilne s ADR-145 release postupkom.

### 9. Priprema za IMAP sinkronizaciju

U Paketu 2 poruke ćemo identificirati stabilnim sastavljenim ključem koji uključuje mailbox, folder, `UIDVALIDITY` i `UID`.

Zato P1-02 mora predvidjeti mogućnost uvođenja takvih relacija, ali **ne stvara još stvarne IMAP poruke, indekse ni sinkronizacijske workere**.
