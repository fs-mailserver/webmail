## 3. Security Audit — model događaja

Predlažem tablicu `audit.security_events` u PostgreSQL-u.

| Polje | Tip | Namjena |
|---|---|---|
| `id` | UUID | Jedinstveni događaj |
| `occurred_at` | timestamptz | Vrijeme događaja |
| `actor_id` | UUID, nullable | Korisnik ili servis |
| `event_type` | Text | Vrsta sigurnosnog događaja |
| `resource_type` | Text | Vrsta resursa |
| `resource_ref` | Text | Kontrolirana referenca |
| `result` | Text | Success, failure, denied |
| `correlation_id` | UUID | Veza s drugim operacijama |
| `metadata` | JSONB | Samo dopušteni metapodaci |
| `prev_hash` | Bytea | Hash prethodnog događaja |
| `event_hash` | Bytea | Hash trenutačnog događaja |

Za `event_hash` predlažem kanonsku serijalizaciju i SHA-256 lančanje.

**Važno:** hash-chain je zaštita za otkrivanje promjena, a ne jamstvo protiv administratora koji može izmijeniti cijeli lanac. Zato trebamo periodično sidrenje završnog hasha u zasebnoj offsite evidenciji s neovisnim pristupnim pravima.

### Obvezni audit događaji u Paketu 1

| Kategorija | Primjeri |
|---|---|
| Authentication | Uspješna/neuspješna prijava |
| Passkeys | Dodavanje i opoziv |
| MFA | Aktivacija, promjena, reset |
| Sessions | Odjava, opoziv, istek |
| RBAC | Dodjela i uklanjanje uloga |
| Mailbox grants | Dodjela, promjena, opoziv |
| Delegations | Kreiranje, istek, opoziv |
| Credentials | Testna rotacija i opoziv |
| Admin Agent | Mock privilegirana operacija |
| Configuration | Promjena sigurnosne postavke |

Audit ne smije sadržavati lozinke, recovery kodove, TOTP tajne, session tokene ili privatni sadržaj poruka.

## 4. Operativni logovi

Predlažem strukturirane JSON logove.

Primjer dopuštenog zapisa:

```json
{
  "timestamp": "2026-11-22T10:00:00Z",
  "level": "INFO",
  "service": "webmail-api",
  "event": "auth.login.completed",
  "request_id": "example-request-id",
  "duration_ms": 84,
  "result": "success"
}
```

Logovi ne smiju sadržavati čitljive tajne ni privatne e-mail podatke.

Predlažem centralni redakcijski sloj s allowlistom dopuštenih polja. Ne oslanjamo se samo na uklanjanje lozinki regularnim izrazima nakon nastanka zapisa.

### Retencija

| Podaci | Trajanje |
|---|---|
| Operativni logovi | 30 dana |
| Sigurnosni audit | 12 mjeseci |
| Kritični / break-glass audit | 24 mjeseca |
| Metrike | Posebna kontrolirana politika |

Ove vrijednosti slijede ADR-141; za retenciju se primjenjuju i pravila pravnih obveza te Legal Holda gdje je relevantno.

## 6. Minimalne metrike za Paket 1

| Metrika | Svrha |
|---|---|
| HTTP request count | Opterećenje FastAPI-ja |
| HTTP error rate | Problemi s API-jem |
| HTTP latency | Performanse |
| Login failures | Sigurnosni signal |
| Active sessions | Kapacitet i sigurnost |
| Celery task failures | Problemi obrade |
| PostgreSQL connection usage | Opterećenje baze |
| Admin Agent failures | Neuspjele simulirane operacije |
| Audit write failures | Kritični sigurnosni signal |

Metrike moraju imati ograničenu kardinalnost. E-mail adrese, session ID-ovi ili message ID-ovi ne koriste se kao metričke oznake.

## 7. Healthchecks

Predlažem tri različita endpointa:

| Endpoint | Namjena |
|---|---|
| `/health/live` | Proces radi |
| `/health/ready` | Servis je spreman prihvaćati promet |
| `/health/dependencies` | Detaljnija dijagnostika, samo ovlašteni pristup |

`liveness` ne treba automatski padati zbog svakog kratkog zastoja PostgreSQL-a, jer bi to moglo izazvati nepotrebne restartove.

`readiness` može signalizirati da servis trenutačno nije sposoban sigurno obraditi zahtjeve.

Detaljni status tajni, konfiguracije i internih servisa ne smije biti javno dostupan.

## 8. GitHub Actions — CI matrica

Predlažem sljedeće provjere za PR.

| Provjera | Alat / pristup |
|---|---|
| Python format i lint | Ruff |
| Python tipovi | Statička analiza |
| Python testovi | pytest |
| TypeScript tipovi | TypeScript compiler |
| Frontend lint | ESLint |
| Frontend testovi | Odabrani test runner |
| OpenAPI contract | Deterministička usporedba |
| PostgreSQL migracije | Izolirana testna baza |
| Dependency audit | Python i npm ekosustav |
| Secret scanning | Obvezno |
| Container scanning | Obvezno za image promjene |
| SBOM | Za release artefakte |
| Security E2E | Playwright i sigurnosni scenariji |

GitHub Actions nema produkcijske lozinke, Docker pristup dedicated serveru niti opće ovlasti za deployment.

### 9. Pravila prolaska CI-ja

Predlažem:

- Protected `main` grana.
- Obvezne statusne provjere.
- PR review prije mergea.
- Zabrana automatskog mergea.
- Zabrana automatskog produkcijskog deploymenta.
- Reproducibilni testni podaci.
- Testovi nezavisni o produkcijskoj infrastrukturi.
- Obvezan pregled promjena sigurnosnih modula i migracija.

CI mora moći završiti i ako produkcijski mailserver nije dostupan.

## 10. Audit failure politika

Ovo je posebno važna sigurnosna odluka.

Za radnje koje mijenjaju sigurnosne ovlasti, recovery, tajne ili privilegiranu konfiguraciju predlažem **fail-closed** ponašanje ako nije moguće pouzdano evidentirati audit.

Drugim riječima, takvu radnju ne izvršavamo ako ne možemo osigurati trajni audit zapis.

Za obične read-only operacije primjenjujemo drugačiju politiku: kratkotrajni problem telemetrije ne mora automatski srušiti cijeli Webmail.

Potrebno je razlikovati **nedostupnost Lokija** od **nedostupnosti sigurnosnog audita**. To nisu isti kvarovi.

Kod kritičnih promjena audit i izmjena stanja trebaju biti transakcijski povezani gdje je izvedivo, a operacije koje imaju vanjski učinak zahtijevaju trajan zapis namjere prije izvršavanja.
