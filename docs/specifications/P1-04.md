## 2. Administratorske uloge

Zadržavamo tri uloge iz ADR-007.

| Uloga | Administrativni opseg | Pristup sadržaju pošte |
|---|---|---|
| **Super Admin** | Globalna konfiguracija, uloge i upravljanje sustavom | Samo uz zaseban mailbox grant |
| **Admin** | Dodijeljene domene i njihovi administrativni resursi | Samo uz zaseban mailbox grant |
| **User** | Vlastiti račun i dopuštene funkcije | Samo odobreni mailboxi |

Za administratora domene pravilo glasi: njegov `domain_scope` mora biti eksplicitno dodijeljen, a ne izveden samo iz e-mail adrese kojom se prijavljuje.

Posebno štitimo posljednjeg aktivnog Super Admina od slučajnog uklanjanja ili suspenzije.

## 3. Granularna mailbox prava

Predlažem da se prava dijele po konkretnim operacijama.

| Pravo | Što dopušta |
|---|---|
| `mail.read` | Pregled poruka, uz autoriziranu pretragu |
| `mail.flags.write` | Read/unread, Star i druge dopuštene zastavice |
| `mail.move` | Premještanje poruka između dopuštenih mapa |
| `mail.delete` | Uobičajeno brisanje prema pravilima mailboxa |
| `mail.send` | Slanje preko odobrenog identiteta pošiljatelja |
| `mail.drafts.write` | Kreiranje i uređivanje nacrta |
| `mail.folders.manage` | Upravljanje dopuštenim mapama |
| `mail.share.manage` | Upravljanje dijeljenjem u dopuštenom opsegu |

**`mail.delete` ne podrazumijeva trajno brisanje.** Trajno brisanje i zaobilaženje retencijskih zaštita zasebne su, strože kontrolirane operacije.

Također, `mail.send` sam po sebi nije dovoljan: backend mora provjeriti ovlašteni sender identity i stvarnu mogućnost SMTP slanja.

## 4. Predloženi PostgreSQL model

Koristimo `access` shemu iz P1-02.

### `access.role_assignments`

| Polje | Tip | Namjena |
|---|---|---|
| `id` | UUID | Primarni ključ |
| `user_id` | UUID | Webmail identitet |
| `role` | Enum/Text | Super Admin, Admin, User |
| `scope_type` | Text | Global ili domain |
| `scope_ref` | UUID / Nullable | Određeni domenski opseg |
| `granted_by` | UUID | Tko je dodijelio |
| `created_at` | timestamptz | Vrijeme dodjele |
| `revoked_at` | timestamptz | Opoziv |

Kod globalne uloge `scope_ref` je prazan, a domenska uloga mora imati valjanu referencu. Ta pravila treba osigurati i ograničenjima baze.

### `access.mailbox_grants`

| Polje | Tip | Namjena |
|---|---|---|
| `id` | UUID | Identifikator granta |
| `user_id` | UUID | Korisnik |
| `mailbox_ref` | UUID | Stabilna interna mailbox referenca |
| `permissions` | Text[] / JSONB | Skup dopuštenih operacija |
| `granted_by` | UUID | Davatelj prava |
| `valid_from` | timestamptz | Početak |
| `valid_until` | timestamptz | Opcionalni istek |
| `revoked_at` | timestamptz | Opoziv |
| `version` | Integer | Kontrola istodobnih promjena |

U Paketu 1 `mailbox_ref` upućuje na kontrolirani sintetički mailbox katalog. Pravi IMAP identitet povezuje se tek u Paketu 2.

### `access.delegations`

| Polje | Namjena |
|---|---|
| `id` | Identitet delegacije |
| `grantor_id` | Izvorni davatelj |
| `delegate_id` | Korisnik kojem se delegira |
| `mailbox_ref` | Ciljni mailbox |
| `permissions` | Dopuštena podskupina prava |
| `valid_until` | Obvezni istek |
| `status` | Pending, active, revoked, expired |
| `approved_by` | Odobravatelj, gdje je potreban |

Delegacija ne smije davati veća prava od onih koja su izričito dopuštena izvornom korisniku za delegiranje. Opoziv izvornog prava mora se odraziti i na izvedenu delegaciju.

## 7. Opoziv prava

Opoziv mailbox granta mora odmah blokirati nove autorizirane API zahtjeve i operacije.

Predlažem sljedeće kontrole:

- Svaka operacija prije izvršavanja provjerava važeća prava.
- Dugotrajni Celery poslovi ponovno provjeravaju prava prije vanjskog učinka.
- WebSocket događaji ne smiju nastaviti otkrivati podatke nakon opoziva.
- Aktivne IMAP veze povezane s opozvanim pravima treba prekinuti gdje je izvedivo.
- Offline PWA cache čisti se kada aplikacija ponovno dobije kontrolu, bez jamstva trenutnog udaljenog brisanja.

Za cache autorizacijskih odluka možemo koristiti kratkotrajnu optimizaciju samo ako postoji pouzdan mehanizam invalidacije. Sigurnosno kritične operacije ne smiju ovisiti o zastarjelom dopuštenju.

## 8. Posebne operacije

### Dijeljeni mailboxi

Više korisnika može imati različite razine prava nad istim mailboxom.

Sve radnje moraju imati audit identitet stvarnog Webmail korisnika, a ne samo zajedničkog IMAP računa.

### Delegacije

Delegacija mora biti vremenski ograničena, opoziva i auditirana.

Ne dopuštamo lančano delegiranje bez zasebne politike.

### Break-glass

Prema ADR-066, izvanredni pristup zahtijeva odvojenu proceduru, neovisnog odobravatelja i snažan audit.

Ne uvodimo skriveni univerzalni administratorski pristup porukama.

### Legal Hold

Zaštićene poruke ne smiju se trajno ukloniti čak ni ako korisnik ima obični `mail.delete` grant.

| `POST /api/v1/access/delegations` | Kreiranje delegacije |
| `DELETE /api/v1/access/delegations/{id}` | Opoziv delegacije |

Svi administrativni endpointi moraju imati zasebne RBAC i step-up kontrole prema riziku.

Odgovori za nedopuštene resurse ne smiju nepotrebno otkrivati postojanje tuđih mailboxa.
